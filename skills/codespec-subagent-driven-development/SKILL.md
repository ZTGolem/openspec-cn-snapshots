# 子智能体驱动开发

通过为每个任务分派一个全新的子智能体来执行计划，每个任务完成后按返回流程图中的审查节点进行审查。

**为什么用子智能体：** 你将任务委派给具有隔离上下文的专用智能体。通过精心设计它们的指令和上下文，确保它们专注并成功完成任务。它们不应继承你的会话上下文或历史记录——你要精确构造它们所需的一切。这样也能为你自己保留用于协调工作的上下文。

**核心原则：** 每个任务一个全新子智能体 + 按流程图审查 = 高质量、快速迭代

## 流程

**本批要执行的 per-task 流程与示例工作流由 `codespec apply-subagent flow` 命令按测试模式动态返回，在开始执行任何任务之前第一步获取。**

在开始执行任何任务之前：

1. **确定测试模式并获取本批执行流程（关键，第一步）**：
   - 先读取 task.md 头部的 `测试策略` 标记（`tdd` / `test-after` / `no-test`）；未找到时默认 `tdd`。
   - 按该模式运行（缺省 flag 时命令默认按 `tdd` 返回）：
   ```bash
   codespec apply-subagent flow --tdd        # 或 --test-after / --no-test
   ```
   - 返回的 dot 流程图即本批实际要执行的 per-task 流程；返回的 example 即本批示例工作流（见下文「示例工作流」一节）。
   - 严格按返回图中的节点与边执行：只为图中出现的 agent 分派子智能体；不添加图中没有的审查步骤，也不跳过图中有的审查步骤。
   - **唯一例外——验证门禁：** 「验收与验证门禁（阻断式）」一节的验收清单与门禁**必须执行**，无论返回图中是否画出了该节点。它由**控制者**执行，不是对图中节点的增补或替换：图里没有验证节点时按该节补上门禁；**绝不允许**因为图里没画就跳过验证。
2. 读取 spec.md, design.md 和 task.md，建立全局需求理解。
   - **在分派第一个实现子智能体之前**，按「验收与验证门禁」第 1 节把需求原文**逐条**落成可执行验收清单（`codespec/changes/<change-name>/acceptance.md`），并把与本任务相关的验收项**随任务完整文本一起**交给实现子智能体。清单未建好之前**不开始任何实现**。
3. 提取所有任务的完整文本与上下文，创建 TodoWrite：**每个任务一个条目**（任务内的实现与图中该任务的各审查节点都是该条目的子步骤，**不要**为子步骤创建条目）。

  **TodoWrite 纪律（关键）：**
  - 在开始实现前，**必须**用 Todo 为所有未完成任务创建条目(**只跟踪任务，不要跟踪子步骤**)
  - 每完成一个任务后，**立即**将其标记为 completed
  - 不要批量标记——完成一个标记一个
  - TodoWrite 是 continuation enforcer 判断进度的基础，不遵守 = 系统误判

  **task.md 复选框同步（关键）：**
  - 每完成一个任务后，**同时**用 Edit 工具更新 `task.md` 文件中的任务复选框
  - 将对应任务的 `### [ ]` 改为 `### [x]`
  - task.md 路径：`codespec/changes/<change-name>/task.md`
  - 确保 task.md 中的复选框状态与 TodoWrite 完成进度保持一致

## 验收与验证门禁（阻断式）

**本节覆盖任何测试策略。** `no-test` 只豁免「编写新的单元测试」，**不豁免本节的任何要求**：验收清单要建、既有测试要跑、失败要定级、证据要留、报告要列未通过用例。验收清单与门禁由**控制者**执行，不属于「实现者编写或运行单元测试」，因此不违反 `no-test` 策略。

### 1. 需求 → 可执行验收清单（分派第一个子智能体之前完成）

在分派第一个实现子智能体之前，读取 spec.md，把**需求原文逐条**落成一份可执行验收清单（写入 `codespec/changes/<change-name>/acceptance.md`，并把与本任务相关的验收项随任务完整文本一起交给每个实现子智能体）。

每条验收项必须写全：

| 字段 | 要求 |
|------|------|
| 需求来源 | spec.md 的章节/条目**原文**（引用原文，不改写、不合并需求） |
| 验收方式 | 可执行的判定手段：既有测试用例（写明 `文件::用例名`）/ 命令 / 可复现脚本 / 明确的可观察行为 |
| 预期结果 | 通过的判定标准（退出码、输出、断言内容） |
| 证据位置 | 该条验收的结果记录在哪（命令输出、清单状态、文件路径） |

规则：
- **一条需求对一条验收项**，不得把多条需求合并成一条「大概覆盖」，也不得留空或写「无」。
- `no-test` 模式下**照样要写**验收方式：可以用既有测试、可以用命令/脚本复现、也可以是「可观察行为 + 审查者逐条核对」，但**不能空**。
- 需求原文有歧义、冲突或缺验收标准时，**先澄清再实现**，澄清结论写回 spec.md；不得由实现者自行揣测需求含义。
- 实现者必须在返回报告中**逐条回填**验收状态（通过 / 未通过 / 未能判定 + 证据），不得只回一句「已完成」。

### 2. 门禁执行（阻断式）

在流程图要求的审查全部通过之后、报告完成之前，控制者必须执行验证门禁：

1. 执行验收清单里的**每一条**验收项，记录命令、退出码与通过/失败数。
2. 运行项目**既有的完整测试套件**（不是新写的测试），记录命令、退出码、通过数、失败数与**失败用例清单**。
   - 「既有测试」= 变更前就存在的测试。**「不修改测试文件」不构成跳过运行既有测试的理由。**
3. 读完整输出、统计失败数；**不依赖任何先前运行结果、推断或「应该会通过」**。
4. 对每一条失败用例做**三分支定级**（见第 3 节），并留存证据。

**阻断规则：** 门禁为红时，**不得**把任务标记为完成、**不得**输出「实现完成」、**不得**进入归档；必须先走第 4 节的修复-复审闭环。

### 3. 失败用例三分支定级（缺证据不得放行）

任何失败用例都**必须**归入以下三分支之一，并且**必须留存证据**。「看起来是预期内的」「官方补丁会更新」「评测环境会替换测试文件」**都不是**合法依据，不能作为免责理由。

**分支 A：基线既有失败（与本次变更无关）**
- 必须提供**基线对比证据**：在**本次变更之前**的代码状态上运行**同一条命令**（例如用 `git worktree` 检出变更前的基线提交，或使用改动前保留的运行输出），得到**相同的失败用例**。
- 证据形式：变更前与变更后的命令、退出码、失败用例名对照，两份输出都要留存。
- **拿不出基线证据的一律按分支 B 处理（阻断）**，不得口头声明「这应该是老失败」。
- 分支 A 的失败**仍然必须列进完成报告的「未通过用例」**，并标注「基线既有失败 + 证据」。

**分支 B：变更引入的回归（阻断）**
- 判定：变更后失败、基线通过；或无基线证据可证为既有失败。
- 处置：修复 → 重跑 → 直到通过。
- **例外（仅当 issue/spec 明确要求该行为变化）**：可以保留失败，但**必须同时**做到：
  1. 在 spec.md / design.md / task.md 中**写明**新的预期行为，并引用需求原文作为依据；
  2. **同步更新**受影响的既有测试/断言，使其断言新行为（此时「不修改测试文件」的旧惯例以本条为准）；
  3. 在完成报告中列出该用例，说明「按需求原文 X 的要求，行为由 A 变为 B」；
  4. 若需求原文并未要求该行为变化，或**无法确认**（依赖版本状态、上游计划等未验证前提），则**不得**走例外，必须修复。

**分支 C：目标行为未达成（阻断）**
- 判定：验收清单中任一条未通过，或某条验收方式无法判定。
- 处置：回到实现补齐该条需求 → 重跑该条验收 → 重新过门禁。

**未决前提的处置（不得凭推断拍板）：** 当范围裁剪、行为变更或兼容策略依赖**本次无法证实的外部前提**（例如目标版本是否已处于某个开发期、该行为是否已废弃、上游是否会同步更新测试）时：
- 不得凭记忆或推断当作既定事实写进 ar.md / design.md / task.md；
- 必须**升级为阻塞项**并记录：**前提是什么 / 证据缺口在哪 / 已尝试过哪些取证方式 / 采用的 fallback 与理由 / 若前提为假的回退动作**；
- 若该前提直接决定**用户可见行为**，在澄清前**不得**放行相关验收项。

### 4. 修复-复审闭环

门禁失败 → 按分支给出处置 → **由实现子智能体**修复（遵循「如果子智能体失败」一节，不手动修复、避免上下文污染）→ 重跑**受影响的**验收项与完整测试套件 → 重新过门禁 → 复审。**循环直到门禁全绿**，或按「暂停时的输出」上报未通过项。

- 修复后必须**重新运行**验证命令，不得引用修复前的输出作为新证据。
- 门禁仍红时**不得**报告完成、不得进入下一个任务、不得输出完成报告。
- 一个门禁节点红 = 本批未完成。

### 5. 证据留存

在 `codespec/changes/<change-name>/verification.md`（或变更目录下等价文件）留存本批门禁证据：

- 每条验收项：需求来源、验收命令/方式、结果、证据（输出片段或文件路径）
- 完整测试套件：命令、退出码、通过数、失败数
- 失败用例清单：每条 → 分支（A/B/C）→ 判定依据 → 基线对比输出（如有）→ 处置结果
- 未决前提与阻塞项：前提、证据缺口、已尝试的取证、fallback 与理由、回退动作

证据必须来自**本次实际运行**；不得写入未运行过的命令或推测的结果。修复后**追加**新的运行记录，保留历史记录不覆盖。

## 处理实现者状态

实现子智能体报告四种状态之一。根据每种状态进行相应处理：

**DONE：** 进入流程图中的下一个审查节点。

**DONE_WITH_CONCERNS：** 实现者完成了工作但标记了疑虑。在继续之前阅读这些疑虑。如果疑虑涉及正确性或范围，在审查前解决。如果只是观察性说明（如"这个文件越来越大了"），记录下来并继续审查。


**疑虑升级规则（阻断式）：** 下列疑虑**不得**作为「附带收益」「预期内」「评审时再说」接受，必须在审查前解决，或升级为阻塞项并按第 3 节记录：

- **行为面外溢**：本次改动会连带改变需求之外的既有行为、公开 API、类型/单位/默认值等契约（例如删除某个转换分支后，既有对象的类型随之改变）。
- **既有测试与本改动直接相关**：实现者指出某条既有用例断言的正是本次要移除的旧行为，或预言某条用例会失败——**只要该用例与本次改动相关，就不能预判它「会被外部更新」而放行**；按第 3 节做基线对比与分支定级。
- **依赖未验证前提**：结论成立与否取决于本次无法证实的外部事实（版本状态、上游计划、第三方会否更新测试等）。

处置：① 本批次内能解决 → 修复并重跑验证；② 需要外部确认 → 按第 3 节「未决前提的处置」记录并升级为阻塞项，**带病不得结案**；③ 与需求原文冲突 → 回到 spec/design/task 澄清后再继续。

**NEEDS_CONTEXT：** 实现者需要未提供的信息。提供缺失的上下文并重新分派。

**BLOCKED：** 实现者无法完成任务。评估阻塞原因：
1. 如果是上下文问题，提供更多上下文并用同一模型重新分派
2. 如果任务需要更强的推理能力，用更强的模型重新分派
3. 如果任务太大，拆分为更小的部分
4. 实施阶段为无人值守，只有在反复尝试仍无法通过时才暂停报告状态（最低优先级）

**绝不** 忽略上报或在不做任何更改的情况下让同一模型重试。如果实现者说卡住了，说明有什么东西需要改变。

## 示例工作流

本批的示例工作流不再硬编码于本技能，而是由 `codespec apply-subagent flow --<tdd|test-after|no-test>` 命令一并返回（JSON 的 `example` 字段，或文本输出的「示例工作流」一节）。其默认值为内置默认示例（以内置默认流程为例；自定义流程图同理，按返回的图执行），用户可在 `config.yaml` 的 `subagent-apply.<mode>.example` 中覆盖。

获取后，参照返回的示例理解控制者与子智能体之间的交互节奏（提问 → 实现 → 自审 → 按流程图审查 → 修复 → 重审 → 标记完成），并按本批实际返回的流程图执行。

> 注意：内置默认示例以 `tdd` / `test-after` 风格展示（含测试步骤）。当本批测试策略为 `no-test` 时，实现者不会编写或运行任何单元测试，示例中的"添加了测试 / N/N 通过"等环节应理解为编译检查与功能自审，而非单元测试。

## 优势

**与手动执行相比：**
- 子智能体严格遵循 task.md 头部标记的测试策略（tdd / test-after / no-test）
- 每个任务全新上下文（不会混淆）
- 并行安全（子智能体不会互相干扰）
- 子智能体可以提问（工作前和工作中都可以）

**效率提升：**
- 无文件读取开销（控制者提供完整文本）
- 控制者精确策划所需上下文
- 子智能体预先获得完整信息
- 问题在工作开始前就被提出（而非工作结束后）

**质量关卡：**
- 自审在交接前发现问题
- 按流程图中的审查节点逐个审查
- 审查循环确保修复确实有效
- 任一审查者报告的每一项问题（关键/重要/次要）都必须完整交给实现子智能体处理，不得摘要、筛选、降级或只选择 bug/关键项
- 规格合规防止过度/不足构建
- 代码质量确保实现良好，验证编译通过

**成本：**
- 更多子智能体调用（每个任务需要实现者 + 流程图中的审查者）
- 控制者需要更多准备工作（预先提取所有任务）
- 审查循环增加迭代次数
- 但能及早发现问题（比后期调试更省成本）

## 红线

**绝不：**
- 未经用户明确同意就在 main/master 分支上开始实现
- 跳过流程图中的审查节点
- 带着未修复的问题继续
- 只修“bug/关键”，跳过“重要/次要”
- 回传审查问题时自行摘要、筛选或只挑关键
- 并行分派多个实现子智能体（会冲突）
- 让子智能体读取计划文件（应提供完整文本）
- 跳过场景铺设上下文（子智能体需要理解任务在哪个环节）
- 忽视子智能体的问题（在让它们继续之前先回答）
- 在审查合规性上接受"差不多就行"（审查者发现问题 = 未完成）
- 跳过审查循环（审查者发现问题 = 实现者修复 = 再次审查）
- 让实现者的自审替代正式审查（两者都需要）
- **不按流程图顺序执行审查**（顺序由图中的边决定，顺序错误）
- 在任一审查有未解决问题时就进入下一个任务

**如果子智能体提问：**
- 清晰完整地回答
- 必要时提供额外上下文
- 不要催促它们进入实现阶段

**如果审查者发现问题：**
- 实现者（同一子智能体）修复
- 审查者再次审查
- 重复直到通过
- 不要跳过重新审查

**如果子智能体失败：**
- 分派修复子智能体并提供具体指令
- 不要尝试手动修复（上下文污染）

**子智能体步骤执行纪律：**
- **严格按步骤顺序** - 实现者子智能体必须严格按计划中的步骤顺序执行，不合并、不跳过、不重排
- **测试策略由计划驱动** - 计划 task.md 头部的 `测试策略` 标记（`tdd` / `test-after` / `no-test`）决定每个任务的步骤形态，必须严格遵循：
  - `tdd`：先写失败测试并确认失败，再写最小实现，再运行测试确认通过
  - `test-after`：先完成功能实现，再编写单元测试覆盖验收场景并运行通过
  - `no-test`：仅实现功能代码并编译检查，**禁止**编写新的单元测试。
    - **`no-test` ≠ 不验证。** 它豁免的是「实现者编写/运行新的单元测试」，**不豁免**「验收与验证门禁」的任何要求：控制者仍必须运行项目**既有**的测试套件、逐条执行验收清单、对失败用例定级、留存证据，并在完成报告中列出未通过用例。
    - **「不修改既有测试文件」不构成跳过运行既有测试的理由**：既有测试必须被运行，并按第 3 节定级。

## 完成时的输出

```
## 实现完成

**变更：** <change-name>
**Schema：** <schema-name>
**执行模式：** subagent
**进度：** 7/7 任务已完成 ✓

### 验收清单（逐条，不合并）
| # | 需求来源（原文） | 验收方式 | 结果 | 证据 |
|---|------------------|----------|------|------|
| 1 | <spec.md 条目> | <命令 / file::test_name> | 通过 | <输出片段 / 文件路径> |
```
