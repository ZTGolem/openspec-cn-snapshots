# 子智能体驱动开发

通过为每个任务分派一个全新的子智能体来执行计划，每个任务完成后按返回流程图中的审查节点进行审查。

**为什么用子智能体：** 你将任务委派给具有隔离上下文的专用智能体。通过精心设计它们的指令和上下文，确保它们专注并成功完成任务。它们不应继承你的会话上下文或历史记录——你要精确构造它们所需的一切。这样也能为你自己保留用于协调工作的上下文。

**核心原则：** 每个任务一个全新子智能体 + 按流程图审查 = 高质量、快速迭代

## 流程

**本批要执行的 per-task 流程与示例工作流由 `codespec apply-subagent flow` 命令按测试模式动态返回，在开始执行任何任务之前第一步获取。**

在开始执行任何任务之前：

1. **确定测试模式并获取本批执行流程（关键，第一步）**：
   - 先读取 task.md 头部的 `测试策略` 标记（`tdd` / `test-after` / `no-test`）；未找到时默认 `tdd`。
   - 按该模式运行（缺省 flag 时命令默认按 `tdd` 返回）：
   ```bash
   codespec apply-subagent flow --tdd        # 或 --test-after / --no-test
   ```
   - 返回的 dot 流程图即本批实际要执行的 per-task 流程；返回的 example 即本批示例工作流（见下文「示例工作流」一节）。
   - 严格按返回图中的节点与边执行：只为图中出现的 agent 分派子智能体；不添加图中没有的审查步骤，也不跳过图中有的审查步骤。
2. 读取 spec.md, design.md 和 task.md，建立全局需求理解。
3. 提取所有任务的完整文本与上下文，创建 TodoWrite：**每个任务一个条目**（任务内的实现与图中该任务的各审查节点都是该条目的子步骤，**不要**为子步骤创建条目）。

  **TodoWrite 纪律（关键）：**
  - 在开始实现前，**必须**用 Todo 为所有未完成任务创建条目(**只跟踪任务，不要跟踪子步骤**)
  - 每完成一个任务后，**立即**将其标记为 completed
  - 不要批量标记——完成一个标记一个
  - TodoWrite 是 continuation enforcer 判断进度的基础，不遵守 = 系统误判

  **task.md 复选框同步（关键）：**
  - 每完成一个任务后，**同时**用 Edit 工具更新 `task.md` 文件中的任务复选框
  - 将对应任务的 `### [ ]` 改为 `### [x]`
  - task.md 路径：`codespec/changes/<change-name>/task.md`
  - 确保 task.md 中的复选框状态与 TodoWrite 完成进度保持一致


### 需求可追溯门禁（关键）

在分派**第一个**实现子智能体之前，从**原始需求来源**（issue / AR 文档 / 用户原话 / spec.md）逐条抽出验收点，形成“需求 → 任务 → 验证”对照表，并当场核对：

- 原始需求中的**每一条**明确要求，都必须在本批任务里有对应任务与验证方式；没有对应的，要么补任务，要么写进对照表的「已推迟」行。
- **不允许静默丢弃需求**：原始需求提出过某项能力（例如“折射/换算/兼容处理”），却在计划阶段被自行判定为“暂不加入”，又没写进 spec 与任务，这就是**需求丢失**，必须补回任务，或显式记录推迟理由并同步到 task.md。
- **禁止向实现子智能体写入与原始需求相悖的指令**（例如“不要实现 X”“X 不在本次范围内”），除非 X 已被记录为显式推迟，且推迟说明写进了 task.md 的对照表。
- 对照表写在 `codespec/changes/<change-name>/task.md` 的任务列表之前（新增一节「需求覆盖对照」），随每次状态更新一起维护。

对照表里每条需求只允许以下两种结论，不允许留空：

- `已覆盖：<需求点> → 任务 N → <验证方式>`
- `已推迟：<需求点> → 推迟理由 → 需要谁确认（用户/待办）`

### 验证与回归门禁（关键）

**基线先行**：在实现第一个任务之前，先跑一遍与本批改动**直接相关**的既有测试并记录基线（例如 `36 failed / 1409 passed / 395 skipped / 26 errors`）。没有基线就分不清“本来就有问题”和“本次改坏的”。

每个任务收尾时：

- 运行与该改动直接相关的既有测试；**任何与本批改动直接相关的既有用例失败，都视为本次改动引入的问题，是阻塞项**，不得写成“预期内/已知问题”后带病收尾。
- 与本批改动无关的既有失败（与基线一致）可以带过，但必须在最终输出里附上基线对比数字。
- 需要区分“既有失败”与“本次引入”时，用 `git stash` / `git stash pop` 对比改动前后同一组用例；对比结束后用 `git status` 确认改动已恢复（改动文件仍为 modified），再下结论。
- 本次新增的目标用例必须全部通过；有任何一个没通过，就不能输出「实现完成」，只能输出降级收尾并写明缺口。

### 增量持久化（关键）

**不要把“已完成什么”只留在对话上下文里。** 会话随时可能被外部运行时取消（限流、超时、SIGTERM），只存在于上下文里的进度会一起丢失，工作区里将没有任何“已完成什么”的记录。

- 实现子智能体返回 DONE 后、**分派审查子智能体之前**，先落盘持久化记录，再继续：
  1. 用 Edit 在 task.md 对应任务小节追加一行状态注解：`> **状态**：实现完成，待审查（测试：<命令> → <结果>）`；复选框**保持** `[ ]`，等审查通过再改 `[x]`。
  2. 在 TodoWrite 里把该任务备注更新为“实现完成、待审查”，**不要**等到审查通过才第一次更新。
- 每通过一个审查节点，同样立即把注解更新为 `> **状态**：规格审查通过，待代码质量审查`（依次推进）。
- 审查全部通过后，才把复选框改成 `[x]`、把 TodoWrite 标为 completed。
- 恢复时先读 task.md 的状态注解与 `git status`，判断每个任务处于“未开始 / 实现完成待审查 / 审查通过”的哪一档，**从断点继续**，而不是从头重做。

## 处理实现者状态

实现子智能体报告下列状态之一。**先判定状态类别，再决定动作**：

- **语义类状态**（DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED）：子智能体正常返回，并给出了可判读的状态结论。
- **传输类失败**（429 限流、超时、5xx、进程被取消/被杀）：子智能体**没有返回任何状态结论**就被外部运行时打断。此时**不得**按语义类状态处理，也**不得**把它当成“实现者说卡住了”——它根本没机会说话。按下方「传输层失败」恢复流程处理。


**DONE：** 进入流程图中的下一个审查节点。

**DONE_WITH_CONCERNS：** 实现者完成了工作但标记了疑虑。在继续之前阅读这些疑虑。如果疑虑涉及正确性或范围，在审查前解决。如果只是观察性说明（如"这个文件越来越大了"），记录下来并继续审查。

**NEEDS_CONTEXT：** 实现者需要未提供的信息。提供缺失的上下文并重新分派。

**BLOCKED：** 实现者无法完成任务。评估阻塞原因（这是**语义性**阻塞：实现者有话说，只是做不完；环境故障/限流不属于本项，见「传输层失败」）：

1. 如果是上下文问题，提供更多上下文并用同一模型重新分派
2. 如果任务需要更强的推理能力，用更强的模型重新分派
3. 如果任务太大，拆分为更小的部分
4. 实施阶段为无人值守，只有在反复尝试仍无法通过时才暂停报告状态（最低优先级）

**绝不** 忽略上报或在不做任何更改的情况下让同一模型重试。如果实现者说卡住了，说明有什么东西需要改变。


### 传输层失败（429 限流 / 超时 / 5xx / 进程被中断）的恢复流程

子智能体**没有返回任何状态结论**就被外部运行时打断（典型报错：`Agent terminated early due to an API error: 429`、`rate_limit`、`overloaded`、超时、5xx、SIGTERM/取消），这是**传输层失败**：既不是语义阻塞，也不是“实现者卡住了”。按以下顺序处理，**不要跳步，也不要先重试**：

1. **先取证，再恢复**（重试之前必须做）：
   - `git status` / `git diff` 查看工作区实际落盘了什么（哪些文件被改、改动是否完整、是否留下半成品）。
   - 读取子智能体最后一条可见输出，提取它已完成的动作（改了哪些文件、跑了哪些测试、结果如何）。
   - 结论只有两种：**产物已完整落盘** 或 **产物不完整**。
2. **产物已完整落盘**：**不要重派整个任务**。把它当作“实现完成、审查待执行”，从流程图的**下一个节点**（审查节点）继续，并按「增量持久化」补记进度（task.md 状态注解 + TodoWrite）。
3. **产物不完整**：只重做**未完成的部分**。分派新的实现子智能体，并显式告知：“前一个子智能体已完成 <X>（文件清单 + 测试结果），你的任务从 <Y> 继续，不要重做 <X>”。
4. **重试必须退避且有上限**：同一任务连续 3 次传输层错误、或累计重试达 10 次仍失败，停止重试，转第 5 步。退避按 1s → 2s → 4s → 8s → 16s → 30s → 30s 递增。**限流时不要换模型、也不要换 agent**——换模型对 429 无效，还会丢掉已经积累的上下文与已落盘的产物。
5. **降级收尾，不要静默归零**：重试耗尽时，**不要**丢弃已落盘的工作，也**不要**输出「实现暂停——需要人工介入」（那是语义阻塞的模板）。改用「完成时的输出」中的**降级收尾模板**，如实写出：已落盘的变更、验证证据、未执行的审查节点、恢复断点。

> 判定口诀：**没有状态结论 = 传输层失败**（等一等、按退避重试、不要换模型）；**有状态结论但说做不完 = 语义阻塞**（换条件再试：补上下文 / 换更强模型 / 拆任务）。

## 示例工作流

本批的示例工作流不再硬编码于本技能，而是由 `codespec apply-subagent flow --<tdd|test-after|no-test>` 命令一并返回（JSON 的 `example` 字段，或文本输出的「示例工作流」一节）。其默认值为内置默认示例（以内置默认流程为例；自定义流程图同理，按返回的图执行），用户可在 `config.yaml` 的 `subagent-apply.<mode>.example` 中覆盖。

获取后，参照返回的示例理解控制者与子智能体之间的交互节奏（提问 → 实现 → 自审 → 按流程图审查 → 修复 → 重审 → 标记完成），并按本批实际返回的流程图执行。

> 注意：内置默认示例以 `tdd` / `test-after` 风格展示（含测试步骤）。当本批测试策略为 `no-test` 时，实现者不会编写或运行任何单元测试，示例中的"添加了测试 / N/N 通过"等环节应理解为编译检查与功能自审，而非单元测试。

## 优势

**与手动执行相比：**
- 子智能体严格遵循 task.md 头部标记的测试策略（tdd / test-after / no-test）
- 每个任务全新上下文（不会混淆）
- 并行安全（子智能体不会互相干扰）
- 子智能体可以提问（工作前和工作中都可以）

**效率提升：**
- 无文件读取开销（控制者提供完整文本）
- 控制者精确策划所需上下文
- 子智能体预先获得完整信息
- 问题在工作开始前就被提出（而非工作结束后）

**质量关卡：**
- 自审在交接前发现问题
- 按流程图中的审查节点逐个审查
- 审查循环确保修复确实有效
- 任一审查者报告的每一项问题（关键/重要/次要）都必须完整交给实现子智能体处理，不得摘要、筛选、降级或只选择 bug/关键项
- 规格合规防止过度/不足构建
- 代码质量确保实现良好，验证编译通过

**成本：**
- 更多子智能体调用（每个任务需要实现者 + 流程图中的审查者）
- 控制者需要更多准备工作（预先提取所有任务）
- 审查循环增加迭代次数
- 但能及早发现问题（比后期调试更省成本）

## 红线


**预算与降级收尾护栏：**

- 本批只有 1 个任务、或改动极小时，**不要**在流程图规定的审查节点之外再自行增加自审轮次、额外验证轮次或“再来一次”；流程图有几个节点就跑几次。
- 分派子智能体时带上完整任务文本，**不要**让子智能体自己去读计划文件（读不全且费时）。
- 察觉会话接近时间/上下文上限时，**主动**在下一个检查点停下来（不要等被外部运行时取消），用「完成时的输出」中的**降级收尾模板**如实输出已落盘内容、验证证据与未执行节点。
- 因传输层失败而做的降级收尾**不算**“带着未修复的问题继续”，但**必须**如实标注哪些审查没做、哪些用例仍失败。

**绝不：**
- 未经用户明确同意就在 main/master 分支上开始实现
- 跳过流程图中的审查节点
- 带着未修复的问题继续
- 只修“bug/关键”，跳过“重要/次要”
- 回传审查问题时自行摘要、筛选或只挑关键
- 并行分派多个实现子智能体（会冲突）
- 让子智能体读取计划文件（应提供完整文本）
- 跳过场景铺设上下文（子智能体需要理解任务在哪个环节）
- 忽视子智能体的问题（在让它们继续之前先回答）
- 在审查合规性上接受"差不多就行"（审查者发现问题 = 未完成）
- 跳过审查循环（审查者发现问题 = 实现者修复 = 再次审查）
- 让实现者的自审替代正式审查（两者都需要）
- **不按流程图顺序执行审查**（顺序由图中的边决定，顺序错误）
- 在任一审查有未解决问题时就进入下一个任务

**如果子智能体提问：**
- 清晰完整地回答
- 必要时提供额外上下文
- 不要催促它们进入实现阶段

**如果审查者发现问题：**
- 实现者（同一子智能体）修复
- 审查者再次审查
- 重复直到通过
- 不要跳过重新审查

**如果子智能体失败：**
- 先判定失败类别（产物失败 vs 传输层中断），再按上方「传输层失败」恢复流程处理
- 产物失败（返回了状态但工作不合格）：分派修复子智能体并提供具体指令
- 传输层中断（没有状态结论）：**先取证工作区**再决定重做范围，**不要**直接重派整个任务
- 不要尝试手动修复（上下文污染）


**子智能体步骤执行纪律：**
- **严格按步骤顺序** - 实现者子智能体必须严格按计划中的步骤顺序执行，不合并、不跳过、不重排
- **测试策略由计划驱动** - 计划 task.md 头部的 `测试策略` 标记（`tdd` / `test-after` / `no-test`）决定每个任务的步骤形态，必须严格遵循：
  - `tdd`：先写失败测试并确认失败，再写最小实现，再运行测试确认通过
  - `test-after`：先完成功能实现，再编写单元测试覆盖验收场景并运行通过
  - `no-test`：仅实现功能代码并编译检查，**禁止**编写或运行任何单元测试

## 完成时的输出

```
## 实现完成

**变更：** <change-name>
**Schema：** <schema-name>
**执行模式：** subagent
**进度：** 7/7 任务已完成 ✓

### 本次会话已完成
- [x] 任务 3：<description>
- [x] 任务 4：<description>
...

### 验证证据
- **基线（改动前）：** `<测试命令>` → <N failed / M passed>
- **改动后：** `<测试命令>` → <N failed / M passed>
- **与本批改动相关的既有用例：** 全部通过 ✓
- **需求覆盖：** task.md「需求覆盖对照」无未确认的「已推迟」项（或列出已推迟项与确认人）

所有任务已完成并通过审查！可以使用 `/codespec/archive` 归档此变更。
```

### 降级收尾模板（传输层中断 / 重试耗尽 / 会话被取消时使用）

**不要**用「实现暂停——需要人工介入」来收尾一个传输层故障——那份模板用于语义性阻塞。降级收尾要**如实报告已落盘的工作**，让接手者（或下一次会话）能从断点继续：

```
## 实现中断——环境故障（代码已落盘，审查未完成）

**变更：** <change-name>
**Schema：** <schema-name>
**执行模式：** subagent
**进度：** <N>/<M> 任务实现完成并通过测试；<K> 个审查节点未执行

### 已落盘的变更
- `<文件路径>`：<改了什么>（实现子智能体已完成并落盘，未回滚）

### 验证证据
- **命令：** `<测试命令>` → <N failed / M passed>
- **基线（改动前）：** `<同一命令>` → <N failed / M passed>
- **与本批改动相关的既有用例：** <全部通过 / 仍有失败：<用例名>，未解决原因：...>

### 未执行的审查节点
- <spec-reviewer / code-quality-reviewer / 最终审查>：未执行（原因：<传输层错误：429 / 超时 / 进程中断>）

### 恢复方式
- task.md 已按 `> **状态**：实现完成，待审查` 标注断点；恢复时先读 task.md 与 `git status`，从下一个未执行节点继续，**不要**重做已落盘的实现。

**已落盘的代码与测试证据保留在工作区，未回滚。**
```
