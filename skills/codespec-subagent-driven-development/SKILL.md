# 子智能体驱动开发

通过为每个任务分派一个全新的子智能体来执行计划，每个任务完成后按返回流程图中的审查节点进行审查。

**为什么用子智能体：** 你将任务委派给具有隔离上下文的专用智能体。通过精心设计它们的指令和上下文，确保它们专注并成功完成任务。它们不应继承你的会话上下文或历史记录——你要精确构造它们所需的一切。这样也能为你自己保留用于协调工作的上下文。

**核心原则：** 每个任务一个全新子智能体 + 按流程图审查 = 高质量、快速迭代

## 流程

**本批要执行的 per-task 流程与示例工作流由 `codespec apply-subagent flow` 命令按测试模式动态返回，在开始执行任何任务之前第一步获取。**

在开始执行任何任务之前：

1. **确定测试模式并获取本批执行流程（关键，第一步）**：
   - 先读取 task.md 头部的 `测试策略` 标记（`tdd` / `test-after` / `no-test`）；未找到时默认 `tdd`。
   - 按该模式运行（缺省 flag 时命令默认按 `tdd` 返回）：
   ```bash
   codespec apply-subagent flow --tdd        # 或 --test-after / --no-test
   ```
   - 返回的 dot 流程图即本批实际要执行的 per-task 流程；返回的 example 即本批示例工作流（见下文「示例工作流」一节）。
   - 严格按返回图中的节点与边执行：只为图中出现的 agent 分派子智能体；不添加图中没有的审查步骤，也不跳过图中有的审查步骤。
   - **例外（关键）：**「不添加图中没有的审查步骤」只约束**子智能体审查节点**（spec-reviewer / code-quality-reviewer 等），**不约束控制者亲自执行的「验收与回归门禁」**。返回的图里没有验证节点时，那一步必须由你补上——它不是「可以省略的节点」。`no-test` 模式返回的图通常只含「实现 → 规格审查 → 代码质量审查」，**不含**验收门禁；这正是最容易让整条链路失守的位置。
2. 读取 spec.md, design.md 和 task.md，建立全局需求理解。
3. 提取所有任务的完整文本与上下文，创建 TodoWrite：**每个任务一个条目**（任务内的实现与图中该任务的各审查节点都是该条目的子步骤，**不要**为子步骤创建条目）。

  **TodoWrite 纪律（关键）：**
  - 在开始实现前，**必须**用 Todo 为所有未完成任务创建条目(**只跟踪任务，不要跟踪子步骤**)
  - 每完成一个任务后，**立即**将其标记为 completed
  - 不要批量标记——完成一个标记一个
  - TodoWrite 是 continuation enforcer 判断进度的基础，不遵守 = 系统误判

  **task.md 复选框同步（关键）：**
  - 每完成一个任务后，**同时**用 Edit 工具更新 `task.md` 文件中的任务复选框
  - 将对应任务的 `### [ ]` 改为 `### [x]`
  - task.md 路径：`codespec/changes/<change-name>/task.md`
  - 确保 task.md 中的复选框状态与 TodoWrite 完成进度保持一致

## 验收与回归门禁（阻断式；`no-test` 同样适用）

**这一步由你（控制者）亲自执行，不属于「子智能体审查节点」。返回的流程图里没有它，也必须执行。**

### 为什么存在

`no-test` 是**测试编写策略**，不是**验证豁免**。它限制的是「你不能新增/改写测试文件」，不是「你不能运行仓库里已经存在的测试」。把「不新增/不修改测试」读成「禁止运行任何单元测试」，会关掉破坏性变更唯一的可执行信号：一旦删除某个分支或导出符号，与其直接相关的既有测试失败就会在实现 → 规格审查 → 代码质量审查 → 结案的整条链路上无人发现，最后被当作「预期内」带病收尾。

### 何时做

- 每个任务实现完成后、进入该任务的规格审查**之前**；
- 全部任务完成、输出结案报告**之前**，再做一次覆盖全量的门禁。

只要本次改动**改变了公共行为**（删除/改写分支、移除导出符号、改变返回类型或语义、改变默认值或告警行为），本门禁**必须**执行，不得以「编译通过」代替。

### 怎么做

1. **把需求逐条落成可执行验收。** 读需求原文（spec.md / 用户原始诉求 / 本任务「任务目标」），逐条写下一句**可判定**的验收问题（例如「结构化 ndarray 输入产出的列类型是什么」）。禁止用「应该没问题」「符合预期」这类不可判定的说法代替。
2. **为每条验收定位既有可执行检查。** 优先找仓库里**已经存在**、覆盖该行为的测试（精确到文件与用例名）。no-test 下不得**新增或修改**测试文件，但**运行**既有测试不受此限制。
3. **运行受影响范围的既有测试。**
   - 先跑受影响子包/模块的**完整**测试集合，再跑与需求直接相关的用例。**不要只跑你改动的那一个文件**：删除或改名一个公共 API 之后，破坏常常出现在**依赖它的其他文件**里（模块级 `conftest.py`、共享 fixture、以「模块.属性」形式引用该符号的地方，会在收集/导入期就炸）。
   - 范围拿不准时**向上扩大**（整个子包 → 整个测试目录），不要向下收窄。
4. **读完整输出**：退出码、通过数、失败数，**逐条列出失败用例**，不要只看摘要行。
5. **对每个失败分类**（只有两类，没有第三类）：
   - **与本次改动直接相关** → **阻断**。修复实现并重跑通过；或把它作为**明确记录的未解决阻塞项**升级到报告中。**不得**标为「预期内」「旧行为已废弃」「官方补丁会更新」。
   - **与本次改动无关的基线既有失败** → 只有**拿到证据**才可降级：在**改动前的基线**上（`git stash`、独立 worktree，或 `git show <base>:<file>` 还原后）运行**同一条**用例、同样失败，才算基线失败。「印象里一直是坏的」「与某个依赖版本不兼容」**不是**证据。
   - **计划或任务书里预先写下的免责说明**（例如「该用例断言的是被本次变更移除的旧行为，交付后由官方补丁更新」）**只是待验证的假设，不是结论**：在拿到上面的基线证据之前，不得据此把失败排除在门禁之外，也不得在结案时引用它作为免责依据。
6. **阻断的处理**：与本次改动直接相关的失败在修复并重跑通过之前，该任务**不得**标记完成、不得进入下一个任务、不得结案。

### 与审查节点的分工

| 节点 | 能发现什么 | 发现不了什么 |
|------|-----------|--------------|
| 规格审查（spec-reviewer） | 实现是否**符合规格** | 是否**破坏了规格之外**的既有行为 |
| 代码质量审查（code-quality-reviewer） | 代码**写得好不好** | 旧行为**是否还在** |
| **验收与回归门禁（你）** | **运行既有测试得到的真实回归结果** | —— |

破坏性变更的信号在**运行结果**里，不在代码阅读里。两者都不能替代本门禁。

### 硬性要求

- 门禁必须产出**可复述的证据**：命令 + 退出码 + 通过/失败数 + 失败用例清单。
- 没有运行过受影响的既有测试，**不得**宣称任务完成或批次完成。

## 处理实现者状态

实现子智能体报告四种状态之一。根据每种状态进行相应处理：

**DONE：** 进入流程图中的下一个审查节点。

**DONE_WITH_CONCERNS：** 实现者完成了工作但标记了疑虑。在继续之前阅读这些疑虑。如果疑虑涉及正确性或范围，在审查前解决。如果只是观察性说明（如"这个文件越来越大了"），记录下来并继续审查。

**行为面外溢的疑虑一律按阻塞项处理（关键）：** 如果实现者提出「本次改动会连带改变 X 的公共行为 / 移除某个分支 / 改变返回类型 / 丢弃或保留某种元数据」，或预言「依赖该行为的测试会失败」——即使实现者自己认为这是「附带收益」「副作用可接受」，也**不得**当作附带收益接受，**不得**降级为观察性说明。必须先：(1) 读代码核实该结论是否属实（不采信描述）；(2) 按「验收与回归门禁」跑出受影响既有测试的**实际**结果；(3) 把「本次改动是否被授权改变该公共行为」作为**待决问题**升级到计划与报告中。

**未经外部证据确认的范围裁剪同样按阻塞项处理（关键）：** 如果你或实现者为了「只做最小改动」裁剪了需求原文中的**过渡期行为**（例如需求写明「先加告警过渡、后续版本再移除」，你却直接移除且不加告警），必须先取得外部证据（上游仓库状态、版本策略、changelog、维护者口径）确认该裁剪成立。拿不到证据时，**不得**以自身记忆或推断拍板：要么按需求原文实现过渡期行为，要么把它作为**明确记录的阻塞项**升级，**不得**当作「预期内」带病结案。

**NEEDS_CONTEXT：** 实现者需要未提供的信息。提供缺失的上下文并重新分派。

**BLOCKED：** 实现者无法完成任务。评估阻塞原因：
1. 如果是上下文问题，提供更多上下文并用同一模型重新分派
2. 如果任务需要更强的推理能力，用更强的模型重新分派
3. 如果任务太大，拆分为更小的部分
4. 实施阶段为无人值守，只有在反复尝试仍无法通过时才暂停报告状态（最低优先级）

**绝不** 忽略上报或在不做任何更改的情况下让同一模型重试。如果实现者说卡住了，说明有什么东西需要改变。

## 示例工作流

本批的示例工作流不再硬编码于本技能，而是由 `codespec apply-subagent flow --<tdd|test-after|no-test>` 命令一并返回（JSON 的 `example` 字段，或文本输出的「示例工作流」一节）。其默认值为内置默认示例（以内置默认流程为例；自定义流程图同理，按返回的图执行），用户可在 `config.yaml` 的 `subagent-apply.<mode>.example` 中覆盖。

获取后，参照返回的示例理解控制者与子智能体之间的交互节奏（提问 → 实现 → 自审 → 按流程图审查 → 修复 → 重审 → 标记完成），并按本批实际返回的流程图执行。

> 注意：内置默认示例以 `tdd` / `test-after` 风格展示（含测试步骤）。当本批测试策略为 `no-test` 时，实现者**不编写、不修改**测试文件：示例中的「添加了测试」环节**不适用**；但示例中的「运行测试确认通过」环节**仍然适用**——它运行的是仓库中**既有**的测试，属于「验收与回归门禁」，不是新增测试。`no-test` 限制的是「写测试」，不限制「跑既有测试」。

## 优势

**与手动执行相比：**
- 子智能体严格遵循 task.md 头部标记的测试策略（tdd / test-after / no-test）
- 每个任务全新上下文（不会混淆）
- 并行安全（子智能体不会互相干扰）
- 子智能体可以提问（工作前和工作中都可以）

**效率提升：**
- 无文件读取开销（控制者提供完整文本）
- 控制者精确策划所需上下文
- 子智能体预先获得完整信息
- 问题在工作开始前就被提出（而非工作结束后）

**质量关卡：**
- 自审在交接前发现问题
- 按流程图中的审查节点逐个审查
- 审查循环确保修复确实有效
- 任一审查者报告的每一项问题（关键/重要/次要）都必须完整交给实现子智能体处理，不得摘要、筛选、降级或只选择 bug/关键项
- 规格合规防止过度/不足构建
- 代码质量确保实现良好，验证编译通过

**成本：**
- 更多子智能体调用（每个任务需要实现者 + 流程图中的审查者）
- 控制者需要更多准备工作（预先提取所有任务）
- 审查循环增加迭代次数
- 但能及早发现问题（比后期调试更省成本）

## 红线

**绝不：**
- 未经用户明确同意就在 main/master 分支上开始实现

- 在 `no-test` 模式下把「不新增/不修改测试」当成「禁止运行任何单元测试」
- 没有运行受影响的既有测试就宣称任务或批次完成（编译通过 ≠ 没有破坏既有行为）
- 把与本次改动直接相关的既有测试失败标为「预期内」「旧行为已废弃」「官方补丁会更新」（除非有改动前基线运行的证据）
- 把实现者提出的行为面外溢疑虑当成「附带收益」接受，或用未经外部证据确认的范围裁剪结案
- 跳过流程图中的审查节点
- 带着未修复的问题继续
- 只修“bug/关键”，跳过“重要/次要”
- 回传审查问题时自行摘要、筛选或只挑关键
- 并行分派多个实现子智能体（会冲突）
- 让子智能体读取计划文件（应提供完整文本）
- 跳过场景铺设上下文（子智能体需要理解任务在哪个环节）
- 忽视子智能体的问题（在让它们继续之前先回答）
- 在审查合规性上接受"差不多就行"（审查者发现问题 = 未完成）
- 跳过审查循环（审查者发现问题 = 实现者修复 = 再次审查）
- 让实现者的自审替代正式审查（两者都需要）
- **不按流程图顺序执行审查**（顺序由图中的边决定，顺序错误）
- 在任一审查有未解决问题时就进入下一个任务

**如果子智能体提问：**
- 清晰完整地回答
- 必要时提供额外上下文
- 不要催促它们进入实现阶段

**如果审查者发现问题：**
- 实现者（同一子智能体）修复
- 审查者再次审查
- 重复直到通过
- 不要跳过重新审查

**如果子智能体失败：**
- 分派修复子智能体并提供具体指令
- 不要尝试手动修复（上下文污染）

**子智能体步骤执行纪律：**
- **严格按步骤顺序** - 实现者子智能体必须严格按计划中的步骤顺序执行，不合并、不跳过、不重排
- **测试策略由计划驱动** - 计划 task.md 头部的 `测试策略` 标记（`tdd` / `test-after` / `no-test`）决定每个任务的步骤形态，必须严格遵循：
  - `tdd`：先写失败测试并确认失败，再写最小实现，再运行测试确认通过
  - `test-after`：先完成功能实现，再编写单元测试覆盖验收场景并运行通过
  - `no-test`：仅实现功能代码并编译检查，**禁止编写或修改测试文件**（不新增测试文件、不改写既有断言）
  - `no-test` **不禁止运行既有测试**：「不新增/不修改测试」≠「禁止运行任何单元测试」。把 no-test 扩大解释为「不许跑测试」是误读，等于关闭了唯一可执行的回归信号，视为违反本纪律
  - 任何改动公共行为（删除/改写分支、移除导出符号、改变返回类型或语义、改变默认值或告警行为）的任务，都必须运行受影响的既有测试；该运行属于「验收与回归门禁」，不属于被禁止的「编写测试」

```

**变更：** <change-name>
**Schema：** <schema-name>
**执行模式：** subagent
**进度：** 7/7 任务已完成 ✓

### 验收与回归门禁（no-test 模式同样必填）
- **命令：** `<运行受影响既有测试的命令>`
- **退出码：** <退出码>
- **通过：** <N> / **失败：** <M>
- **失败用例：** <逐条列出；无则写「无」>
- **结论：** 通过 / 阻断（未解决项：<...>）

- [x] 任务 3：<description>
- [x] 任务 4：<description>

```

```
**Schema：** <schema-name>

### 已自主尝试的解决措施
1. <尝试 1：例如，换更强模型重新分派>
2. <尝试 2：例如，拆分任务后重新分派>

任务 5：<具体阻塞原因>

**已完成任务：**
- [x] 任务 1-4
```
