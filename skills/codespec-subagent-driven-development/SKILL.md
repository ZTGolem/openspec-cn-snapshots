# 子智能体驱动开发

通过为每个任务分派一个全新的子智能体来执行计划，每个任务完成后按返回流程图中的审查节点进行审查。

**为什么用子智能体：** 你将任务委派给具有隔离上下文的专用智能体。通过精心设计它们的指令和上下文，确保它们专注并成功完成任务。它们不应继承你的会话上下文或历史记录——你要精确构造它们所需的一切。这样也能为你自己保留用于协调工作的上下文。

**核心原则：** 每个任务一个全新子智能体 + 按流程图审查 = 高质量、快速迭代

**同等重要的第二原则——时间有界：** 审查节点数随任务体量走（小任务走快速通道），每任务与整批都有墙钟预算，审查迭代有上限，预算耗尽即降级交付，而不是把流程一直跑到被运行器取消。详见下文「任务体量分级」「墙钟预算与止损规则」「降级交付与中断兜底」。

**同等重要的第三原则——故障有界、产出保全：** 外部中断（429 限流 / API 错误 / 超时 / 运行器取消）不等于流程失败，但必须有成文的分支与出口：基础设施故障按「子智能体基础设施故障分支」做有界重试与退避；任何时候都保有「产出保全与交付记录」，让工作区里的成果随时可交；中断时按「降级交付与中断兜底」交出成果与缺口，而不是让会话带着正确补丁猝死。

## 流程

**本批要执行的 per-task 流程与示例工作流由 `codespec apply-subagent flow` 命令按测试模式动态返回，在开始执行任何任务之前第一步获取。**

在开始执行任何任务之前：

1. **确定测试模式并获取本批执行流程（关键，第一步）**：
   - 先读取 task.md 头部的 `测试策略` 标记（`tdd` / `test-after` / `no-test`）；未找到时默认 `tdd`。
   - 按该模式运行（缺省 flag 时命令默认按 `tdd` 返回）：
   ```bash
   codespec apply-subagent flow --tdd        # 或 --test-after / --no-test
   ```
   - 返回的 dot 流程图即本批实际要执行的 per-task 流程；返回的 example 即本批示例工作流（见下文「示例工作流」一节）。
   - 严格按返回图中的节点与边执行：只为图中出现的 agent 分派子智能体；不添加图中没有的审查步骤，也不跳过图中有的审查步骤。
2. 读取 spec.md, design.md 和 task.md，建立全局需求理解。
   - **建立验收矩阵（关键，必须在派发第一个实现子智能体之前完成）**：按「需求覆盖度关卡」把**需求原文**（issue / 用户原始请求 / ar.md 需求章节 / spec.md 场景条款）逐条落成可执行验收条目，逐条核对它在 ar.md / design.md / task.md 中的落点，并标出**开放项**、**隐含需求**与**被降级为「非目标」的条目**。矩阵未建立、或存在未处置的降级与漏落点，**不得**派发任何实现子智能体。
3. 提取所有任务的完整文本与上下文，创建 TodoWrite：**每个任务一个条目**（任务内的实现与图中该任务的各审查节点都是该条目的子步骤，**不要**为子步骤创建条目）。

  **TodoWrite 纪律（关键）：**
  - 在开始实现前，**必须**用 Todo 为所有未完成任务创建条目(**只跟踪任务，不要跟踪子步骤**)
  - 每完成一个任务后，**立即**将其标记为 completed
  - 不要批量标记——完成一个标记一个
  - TodoWrite 是 continuation enforcer 判断进度的基础，不遵守 = 系统误判

  **task.md 复选框同步（关键）：**
  - 每完成一个任务后，**同时**用 Edit 工具更新 `task.md` 文件中的任务复选框
  - 将对应任务的 `### [ ]` 改为 `### [x]`
  - task.md 路径：`codespec/changes/<change-name>/task.md`
  - 确保 task.md 中的复选框状态与 TodoWrite 完成进度保持一致

## 回归验证关卡（no-test 分支同样必做）

**这是每个任务的完成前阻断门，不是可选建议。** 「不新增/不修改测试文件」约束的是**测试文件的写**，从来不是**测试的执行**。把二者混同，等于在整条链路上关掉唯一能发现「破坏公共行为」的信号：被删的模块级导入、被移除的自动转换分支、改动的导出路径，往往**只在既有测试的收集期或执行期**才暴露（`AttributeError` / `ImportError` / 断言失败），而编译检查与 import 断言全都看不出来。

**本关卡不与「流程」第 1 步的「不添加图中没有的审查步骤」冲突**：它不是流程图上新增的审查节点或子智能体，而是**实现者任务本身的验证要求**，加上**既有审查节点的前置条件**。

### 适用范围

- **所有模式**（`tdd` / `test-after` / `no-test`）下，只要改动触及**公共行为**就一律执行：公共导出、模块级导入、`__init__` 导出、类型转换、默认值、异常类型、函数签名。
- `no-test` 模式下**不得**新增测试文件、不得修改或删除既有测试文件，但**必须**运行受影响范围内的既有测试。
- 纯注释、文档、格式化等不触及公共行为的改动可跳过，但实现者必须在报告中说明「未触及公共行为」。

### 实现者必须完成的动作（返回 DONE 之前）

1. **圈定受影响面**：列出本次改动删除或改动的每一个**可被外部引用的符号**（模块级导入、导出名、属性名、类/函数名、模块级常量）。
2. **仓库内检索引用点**（关键一步）：对每个符号在整个仓库检索——`from <module> import <Name>` 形式、`<module>.<Name>` 属性形式（含 `pkg.mod.Name` 这类**子模块属性**访问）、以及 `tests/` 与 `conftest.py` 中的使用。命中即说明该符号属于公共行为，删除它就是破坏性变更。
3. **运行受影响的既有测试**：运行受影响模块对应的既有测试文件或测试目录（**只运行、不修改**）。至少要覆盖**收集阶段**能暴露的导入期失败——删除模块级导入的典型表征是 `conftest.py` 或测试模块在 import 期抛 `AttributeError`，导致整个测试目录**无法收集**。
4. **报告真实证据**：给出实际执行的命令与真实输出（通过 / 失败 / 收集错误数）。

**不得**用 `compileall`、`import` 断言或手工片段验证替代测试运行——它们只能证明「没有语法或导入错误」，**不能**证明「既有行为未被破坏」。

### 阻断判定

- 既有测试**因本次改动**而失败或收集失败 → 任务**未完成**：先修复实现。**不得**改测试或删测试来「适配」新行为。

- 既有测试因**环境 / 数据时效**（仓库自带的 leap-second / IERS 表、证书、时区库等过期，或外部依赖过期）而失败，且在**变更前基线**上同样失败 → 记为 **C2**，**不**判为本次引入；此时**不得**改生产代码去「绕开」它，**更不得**改仓库数据文件 / pytest 配置 / warning 过滤器来让它变绿（超出本次变更范围，且会掩盖环境问题）——须在报告中逐条列出（用例 ID + 复现命令 + 基线对照 + 分级 + 处置）。
- 失败用例 ID 随执行入口 / 顺序漂移，或同一用例在不同运行中结果不一致 → 先用**同入口同顺序**复跑确认是**顺序依赖**再分级，不得直接记 A 类（详见「验证门禁失败的处置闭环」）。
- 检索发现受影响符号仍被仓库其它位置引用 → 任务**未完成**：该删除属于破坏性变更，须保留兼容（保留导入 / 保留导出 / 提供别名），或在报告中明确升级给控制者裁决。
- 找不到可运行的既有测试入口 → 在报告中**显式写明**「未找到可运行的既有测试」及检索依据，由控制者决定是否接受；**不得静默跳过**。
- 测试命令无法执行（缺依赖、无权限等） → 报 **BLOCKED / NEEDS_CONTEXT**，**不得**报告 DONE 后靠编译检查蒙混。

### 控制者与审查者的责任

- 分派实现者前，把本节要求**写进实现者的指令**（见「墙钟预算与止损规则」的指令模板）。
- 实现者返回 DONE 前**核对**报告中的测试命令与真实输出；缺失即退回补做，不要自己代跑掩盖。
- **规格审查 / 代码质量审查 / 最终整体审查**均以「受影响面检索 + 既有测试运行」已留痕为前置；审查者须独立复核：被删除或改名的符号是否仍被仓库其它位置（含 `tests/`、`conftest.py`、`pkg.mod.Name` 属性形式）引用；既有测试是否因本次改动失败。上述任一成立即记为**关键问题**，走「实现者修复 → 重新审查」循环。
- 预算不足时允许把回归范围**收窄**到最小受影响测试文件，但**不得整项跳过**；确实无法执行须在报告中显式标注并交控制者裁决。

## 需求覆盖度关卡（需求原文 → 可执行验收矩阵）

**这是派发第一个实现子智能体之前的前置门，也是结项前的收尾门。** 「回归验证关卡」回答的是「**没有弄坏什么**」，本关卡回答的是「**该做的做了没有**」——两者互不替代：回归全绿不代表需求被实现；需求原文里的开放项被写进「不在范围内」也不代表它已被正确处置。

**本关卡不与「流程」第 1 步的「不添加图中没有的审查步骤」冲突**：它不新增子智能体、不新增流程图节点——验收矩阵是**控制者侧**的准备工作，矩阵条目是**实现者任务本身的验收要求**，逐项核对是**既有审查节点的前置条件**（见「验收标准的逐条核对」）。「任务体量分级」的 L0 / L1 快速通道**只减少审查子智能体，不豁免矩阵本身**：L0 任务可用轻量矩阵（只抄录条目 + 逐条结论），但矩阵条目不得为空。

### 一、前置：把需求原文逐条落成可执行验收矩阵（派发第一个实现者之前）

**唯一来源是需求原文，不是 task.md 的任务清单。** 需求原文指：issue / 用户原始请求 / `ar.md` 的需求章节 / `spec.md` 的场景条款。只看 task.md 逐条反推验收标准，等于用「计划写什么就做什么」自证完成——计划漏掉的需求永远查不出来。

**建矩阵的动作（控制者亲自做，不外包给子智能体）：**

1. **逐条抄录**：把需求原文中的**每一个**可观察能力、行为、约束、修复点抄成独立条目，一条不合并。抄录时**保留原文引用**（issue 段落 / 原句），不得改写成自己的概括——概括会丢掉限定语，而限定语常常正是验收点。
2. **标出三类最容易漏掉的条目**（漏掉它们是本关卡最常见的失败模式）：
   - **开放项 / 条件项**：原文里「我可以做但需要确认」「如果有需要我可以加」「还没做 X」这类**把决策权留给后续**的表述。它们是**未决需求**，不是**非目标**。
   - **隐含需求**：由原文语境**推导出的等价性 / 一致性约束**——例如「用新路径替换旧路径」隐含「新路径不得丢失旧路径已有的能力」；「新增接口」隐含「不得破坏既有调用方」；「修复缺陷」隐含「该缺陷不得在其它路径上重现」。
   - **负向要求与阶段约束**：原文明说的「不要做什么」「保持 X 不变」，以及分阶段实施要求（先加过渡告警、后移除分支）这类**顺序约束**。
3. **落成可执行验收**：每条必须写清**可执行的验收方式**——具体到「跑哪条命令 / 断言哪个可观察结果 / 检查哪个行为」，而不是「功能可用」「逻辑正确」这类无法判定真假的描述。写不出可执行验收的条目，说明需求本身没澄清，**不得**由控制者自行脑补成「不需要做」，应作为歧义项升级。
4. **记来源与对应任务**：每条注明在 ar.md / design.md / task.md 中对应哪一节、哪个任务，或标注「**未落点**」。

### 二、降级核对（矩阵 vs ar.md / design.md / task.md）

矩阵建好后，逐条核对每个条目在下游产物中的落点，并按下表判定：

| 情形 | 判定 | 处理 |
| --- | --- | --- |
| 条目在 task.md 有对应任务 | 覆盖 | 正常派发 |
| 条目在 ar.md / design.md 存在但 task.md 无对应任务 | **静默漏实现** | 阻断：补任务或走「显式升级」 |
| 条目被写成「不在范围内 / 非目标 / 后续再说」 | **静默降级** | 阻断：见下方规则 |
| 条目标注「未落点」 | 需裁决 | 阻断：升级给用户 / 上层，结论写回产物与矩阵 |

**降级与升级规则：**

- 需求原文**没有**说某项不在范围内，而产物把它写成非目标 → 一律视为**静默降级**，阻断结案。
- 「非目标」只允许两种来源：**需求原文明写排除**（须引用原文），或**用户 / 上层明确裁决**（须留裁决记录）。控制者的**推断**（「看起来不重要」「上游大概会更新」「应该没人用」「实现者说这是预期变化」）**不构成**排除依据。
- 需求原文把决定权留给后续（开放项）的条目，**不得**由控制者单方面定为非目标：必须走「显式升级」拿到明确结论（做 / 不做 / 待定），结论写回 ar.md / design.md / task.md 与矩阵。裁决为「不做」时，该条目仍须作为**已知能力缺口**记入完成报告，不得从报告里消失。
- 需求原文未写、但**不写就明显不成立**的能力（隐含需求），按「静默漏实现」处理：要么补任务，要么显式记为已知缺口并升级。
- 需求原文里的**过渡 / 分阶段要求**（先加告警再移除）不得被压缩成「直接移除」；两段式要求要拆成两条验收条目分别核对。

### 三、收尾：逐项核对（每个任务完成前 + 结项前）

1. **每个任务完成前**：实现者返回的报告中必须**逐条**给出该任务覆盖的验收条目状态（已满足 / 未满足 / 部分满足 / 无法判断）+ 证据（实际命令与输出，或实现位置 + 覆盖它的既有测试）。
2. **结项前**（最终整体审查的前置条件）：矩阵每一条都必须有终态，**不允许留空**。未满足 / 部分满足 / 无法判断 → 记为**关键问题**，走「实现者修复 → 重新审查」；预算不足则走「降级交付」，并在完成报告中**逐条列出未满足条目**。
3. **覆盖度不得只报结论**：必须给出「N/M 条已满足」与未满足条目清单；不得只写「需求已覆盖」「实现完整」「功能均已实现」。
4. **矩阵与产物不一致**：结项时若 ar.md / design.md / task.md 与矩阵仍不一致，以**需求原文**为准，并把差异修回产物或升级；不得在报告里含糊带过。

### 四、矩阵的留存

矩阵默认保留在控制者上下文中（**不落盘**，避免污染变更目录与归档）；确需落盘时写入 `codespec/changes/<change-name>/acceptance-matrix.md`，并在归档前删除。无论哪种形式，**完成报告里必须有「验收覆盖」小节**（见「完成时的输出」），逐条列出条目与终态。


## 验证门禁失败的处置闭环（阻断式）

**门禁失败可以被打断处理，但不能被单方面结案。** 验证节点实测出失败之后只有三条合法出路：**修**、**升级**、**降级交付**；没有第四条「自行认定这是预期行为变化，然后直接放行并结案」。

### 第一步：失败分级（判定必须基于证据，不得基于解释）

| 级别 | 判定依据 | 是否阻断结案 |
| --- | --- | --- |
| **A 类·本次引入** | 同一条测试在**变更前基线**上通过、在**变更后**失败 | **阻断**：必须修复，或走「显式升级」 |
| **B 类·既有问题** | 变更前后**都**失败（基线本来就红） | 不阻断，但必须逐条列出 |
| **C 类·环境/依赖** | 收集错误、缺依赖、无权限、命令无法执行 | 阻断为 BLOCKED，需补环境后重跑 |


**C 类有两种形态，必须分别处置：**

| 形态 | 判定依据 | 处置 |
| --- | --- | --- |
| **C1·跑不起来** | 收集错误、缺依赖、无权限、命令无法执行 | 阻断为 BLOCKED，补环境后重跑 |
| **C2·跑起来了但因环境 / 数据时效而失败** | 失败源是**仓库自带或外部的时效性资源已过期 / 失效**（leap-second / IERS 表、证书、时区库 / tzdata、数据快照与固件镜像等），且与本次改动**无因果关系** | 不阻断结案（不是本次引入），但**必须**逐条写进「未通过用例」，并附复现入口与证据 |

**判 C2 必须有证据，不得凭感觉**：同一条命令在**变更前基线**上**同样失败**（基线取法与「同入口同顺序」要求见下），或失败断言 / 失败栈与本次改动的符号、调用路径无交集（引用点检索结论 + 失败位置）。只拿到变更后的失败输出 → **不得**判 C2，一律按 A 类阻断处理。

**基线对比是硬要求。** A/B 判定必须来自**同一条命令在变更前后各跑一次**的真实输出（变更前基线用 `git stash` / 临时 worktree / `git worktree add` 取 HEAD 版本获得）。**只有变更后的失败输出、没有变更前的对照输出 → 不得分级，一律按 A 类阻断处理。**


**基线对照的取法必须与「不得改写工作区」一致**：用 `git show HEAD:<path>` / `git diff HEAD -- <path>` 取 HEAD 版本，或新建**独立临时 worktree**（`git worktree add <tmp> HEAD`）；**不得**用 `git stash` / `git checkout` / `git restore` / `git reset` 收起当前工作树——那会把已落盘、且已通过前序审查的改动整体收走（见「产出保全与交付记录」的「不得改写工作区」）。本节原推荐 `git stash` 取基线，与该红线直接冲突：控制者若照做取基线，先违反红线，再失去工作区，故在此明确取法。

**「同一条命令」= 同一执行入口 + 同一选择范围 + 同一顺序**：变更前 / 变更后各跑一次，但两次必须覆盖**同一批用例**、以**同一顺序**执行；只跑部分用例、或两次的范围与顺序不同，对照无效（按 A 类阻断处理，重新取对照）。

**顺序依赖与失败用例漂移（必须单独识别，不得混进 A 类）**：有些失败的触发条件是**进程内第一次**发生某类操作，而不是代码本身有错。典型例子：仓库自带的 leap-second / IERS 数据文件已过期，**第一次**做 UTC→TAI 时间换算时抛出过期告警，而仓库 pytest 配置把该告警升级成 error，于是**同一个 pytest 进程里第一个做时间换算的用例**必然失败，其后的换算不再触发、全部通过。这类失败的特征：

- **失败用例 ID 会随执行入口漂移**：先跑哪个文件、是否整目录连跑，决定了哪个用例成为「第一个触发者」，代码没变，用例 ID 却不同（同一份代码下，会话内落在一个时间换算用例、另一执行入口下落在另一个用例）；
- **单独跑该用例可能通过、整文件连跑才失败**（或相反），同一用例在不同运行中结果不一致。

识别与处置：

1. 基线对照必须**同入口同顺序**跑，确认变更前失败的是**同一入口下的第一个触发用例**；
2. 漂移或不稳定 → 判为 **C2（环境 / 数据时效）**，不是 A 类；报告中写明「失败用例 ID 随执行入口漂移」、**复现命令**（含执行入口与顺序）与基线对照结论；
3. **不得**为了让验证变绿去修改仓库自带的时效性数据文件、pytest 配置或 warning 过滤器——那是超出本次变更范围的改动，且会掩盖环境问题；应作为已知缺口 / 待升级项逐条列出；
4. 若该数据更新**确属**任务范围（需求原文明写要更新它），它必须是验收矩阵里的**独立条目**，并按「需求覆盖度关卡」逐条核对，不得混进实现的附带改动。

### 第二步：三条合法出路

1. **修（A 类默认出路）**：交回实现者修复 → 重新运行受影响测试 → 重新审查。**不得**改测试或删测试来「适配」新行为。
2. **显式升级（A 类的唯一例外）**：当且仅当以下**四要件同时成立**，才可判为「issue 明确要求的行为变化」：
   - 要件 1：引用 issue / spec / design 中**明确要求**该行为变化的原文（不得是推测，不得是「大概率会更新」）；
   - 要件 2：spec / design / plan 中与该行为相关的条款**已同步更新**，不留自相矛盾；
   - 要件 3：受影响的既有用例**逐条列出**（用例 ID + 失败断言 + 变更前后对照输出）；
   - 要件 4：该处置**升级**给用户/上层裁决并得到明确结论——**控制者不得自行认定并结案**。

   四要件缺任一项 → 回到出路 1；确实修不了 → 走出路 3。
3. **降级交付**：预算不足、或问题在剩余预算内修不完 → 走「降级交付与中断兜底」，**未通过用例必须逐条写进完成报告**，不得以「预期行为变化」之名消失。

### 不构成豁免的说法（红线）

以下推理**不构成**豁免理由；任何一条出现，结案即无效，必须回到出路 1：

- 「官方测试补丁大概率会更新这些期望」——对尚未落地的补丁的**预测**，不是证据；上游未合并、补丁未应用时，既有用例的失败就是真实回归。
- 「这个测试肯定过时了」——未做基线对比即断言，等于把未证实的假设当结论。
- 「失败数量很少 / 量级很小」——量级不是判据，既有行为被改变就是被改变。
- 「实现者已经说明这是预期变化」——说明 ≠ 需求；需求只在 issue / spec / design 里。
- 「验证者知道这件事，不用再查」——见下条禁止预设立场。

### 禁止在验证指令中预设立场

控制者分派**验证 / 审查子智能体**时，**不得**在指令里写「已知有 X 个预期失败，不必修」「这是官方补丁会更新的行为，照办即可」这类**免责定性**。这类表述会让验证者放弃独立复现，等于把门禁交给控制者的先验判断。

- 控制者已有怀疑时，正确写法是把它列为**待核查假设**，并要求验证者给出**反证**：例如「怀疑 `test_gcrs_altaz_bothroutes` 的失败由新增直连路径引起——请自行用变更前后对照确认或推翻，并给出真实命令与输出」。
- 验证者必须**独立**跑出失败清单与基线对照，**不得**沿用控制者提供的失败名单或结论。

### 验收标准的逐条核对

- 审查 / 验证子智能体必须把 issue / spec 中的**验收标准逐条**列出，标注「已满足 / 未满足 / 无法判断 / 与实现冲突」，**不得**只给整体结论。
- 核对对象是「需求覆盖度关卡」的**验收矩阵**，不是实现者自述的完成清单：审查者必须自行回到**需求原文**复核条目是否被正确落点与实现，**不得**沿用实现者或控制者给出的条目划分与结论。
- 任一条标为「未满足」或「与实现冲突」→ 记为**关键问题**，走「实现者修复 → 重新审查」闭环；实现者上报的偏差与审查者自己发现的偏差**同等处理**，不得因「实现者已经说明过了」而放过。
- 「不在范围内 / 非目标」的条目**同样要核对**：须确认该排除有**原文依据或裁决记录**；只有推断依据的，按**静默降级**记为**关键问题**，走「验证门禁失败的处置闭环」的升级裁决。
- 结论必须落到**逐条状态 + 证据**（跑过哪条命令、看到什么结果）；「看起来覆盖了」「基本都实现了」不算结论。

### 末节点与结项的前置条件

- **最终整体审查**（流程图末节点）必须核对：失败是否已按 A/B/C 分级、未通过用例清单是否为空或已逐条升级、结项报告是否列出了全部未通过用例。任一不满足即**不得进入结项**，回到实现者修复循环。

- 分级为 **C2（环境 / 数据时效）** 的失败：须核验**同入口同顺序**的变更前基线对照确实存在且结论一致（同一入口下失败的是同一个触发用例）；对照缺失或入口不一致 → 按 A 类阻断处理。**不得**因「这是环境问题、与本次改动无关」而跳过核验，也不得让它从「未通过用例」清单里消失。
- **完成报告**必须包含「未通过用例」小节（见「完成时的输出」）；仍有未通过用例时，**不得**写「变更级验证 ✅」，**不得**写「所有任务已完成并通过审查」。

## 任务体量分级（快速通道）

**不要对所有任务一视同仁。** 「每个任务 3 个子智能体 + 返修重审 + 全部任务后再整体审查」会把 3 个小任务放大成 10 次串行往返，足以吃光整个会话预算，最后任务做不完、总结也输出不出来。开始执行前，先按 task.md 给每个任务定级；分级结果写进该任务的 TodoWrite 描述，便于事后审计。

**分级判据（按改动面，不按任务条数）：**

| 级别 | 判据 | 实际执行的审查节点 |
| --- | --- | --- |
| **L0 极小** | 只改变更日志 / 文档 / 注释 / 版本号等非运行时产物；或 ≤2 行的配置、样板文本 | 实现者自审即可，**不分派**规格审查与代码质量审查子智能体 |
| **L1 小** | 单文件、单函数级改动，预计新增/修改 ≤30 行 | 实现者 → 规格审查；**跳过**代码质量审查子智能体 |
| **L2 常规** | 跨多文件、>30 行，或触及运行时行为 | 实现者 → 规格审查 → 代码质量审查（默认级别） |
| **L3 大** | 涉及架构、公共接口、跨模块重构 | 先按「处理实现者状态」中的拆分策略拆成 L2 子任务，再执行 |

**约束：**
- 跳过只针对**审查子智能体**；实现者子智能体内部的实现、自审、编译 / 测试检查一步都不能省。
- 多个 L0 任务可由**同一个**实现子智能体一次批量完成，但每完成一个仍要立即更新 TodoWrite 与 task.md 复选框。
- 涉及运行时行为、错误处理、公共 API、并发或资源管理的任务一律**不低于 L2**，不得为了省时间降级。
- 分级有疑问时取**更小**的一级；预算紧张时优先把 L2 / L3 任务做完，L0 / L1 收尾批量处理（task.md 显式规定执行顺序时以 task.md 为准）。
- 本节是「流程」第 1 步「不跳过图中审查步骤」的**唯一授权例外**：只允许**减少**审查节点，不得添加图中没有的节点；与其它条款冲突时以本节与「红线」的例外条款为准。

## 处理实现者状态

实现子智能体报告四种状态之一。根据每种状态进行相应处理：

**DONE：** 进入流程图中的下一个审查节点。

**接受 DONE 的前置条件（回归验证关卡）：** 报告必须包含「受影响既有测试」的真实执行命令与结果，以及受影响符号的仓库内引用点检索结论。缺任一项即**不接受 DONE**——退回补做；补不回来按 BLOCKED 处理。只有 `compileall` / import 断言 / 手工片段验证不算完成。

**接受 DONE 的前置条件（验收条目）：** 报告还必须给出该任务覆盖的验收条目**逐条**状态（已满足 / 未满足 / 部分满足 / 无法判断）与证据（实际命令与输出，或实现位置 + 覆盖它的既有测试）。缺失、含糊（「基本都实现了」）或用「不在范围内」代替逐条结论 → **不接受 DONE**，退回补做；实现者自行把开放项判为非目标而未升级的，视为**静默降级**，退回并升级裁决。

**接受 DONE 的前置条件（报告内的警告与失败证据）：** 报告正文里**只要**出现「某既有测试会失败 / 某处只差一步没接上 / 官方测试补丁会覆盖」这类**警告、失败证据或未闭环的疑虑**，就**不得**按 DONE 受理——一律按 **DONE_WITH_CONCERNS** 处置，逐条走「疑虑」分支。控制者读到了疑虑却不做处置就进入审查节点，等同于「接受 DONE 的前置条件」未通过。实现者把失败归因于「官方测试补丁会覆盖」「上游会更新」，属于「不构成豁免的说法」，**不是**可以带进审查节点的结论：既有测试失败必须先按「验证门禁失败的处置闭环」做**变更前基线对照**与 A/B/C 分级。

**接受 DONE 的前置条件（产出已落盘核实）：** 控制者必须逐条核对报告声称的改动**在工作树里真实存在**（`git status --short` + 抽查关键符号），尤其是**接线类改动**——新模块的**导入 / 注册 / 导出 / 挂载点**必须在工作树里能看到对应的那一行，而不是「文件建好了、功能没接上」。只建文件、不接线，等于**功能从未生效**：这类「报告说改了、树里只建了一半」的情况按**关键问题**处理，退回补做，**不得**进入审查节点，**不得**在报告里写成「已完成」。

**DONE_WITH_CONCERNS：** 实现者完成了工作但标记了疑虑。**疑虑是待处置项，不是备注。** 在继续之前阅读每一条疑虑，并为**每一条**给出明确处置（已修复 / 非阻塞且附理由 / 阻塞并升级）：

- 疑虑指向**验收标准、期望输出、规格符合性或公共行为** → 必须走「实现者修复 → 重新审查」循环，**不得**仅记录后放行；未闭环前该任务**不得**进入下一个节点，**不得**被计为完成。
- 疑虑指向**正确性或范围** → 在进入审查前解决。
- 仅是观察性说明（如"这个文件越来越大了"）→ 记录并继续审查，但**仍须**写进最终报告的遗留问题。
- 疑虑**无法在剩余预算内修复** → 按严重级分流：阻塞项走「降级交付」，并在完成报告中逐条列出。

**DONE_WITH_CONCERNS 不得在无逐条处置的情况下被接受为 DONE。** 实现者上报的验收偏差与控制者自行发现的偏差同等对待：都要走「修复 → 复审」闭环；实现者已上报的偏差不构成单方面结案的依据。

**NEEDS_CONTEXT：** 实现者需要未提供的信息。提供缺失的上下文并重新分派。

**BLOCKED：** 实现者无法完成任务。评估阻塞原因：
1. 如果是上下文问题，提供更多上下文并用同一模型重新分派
2. 如果任务需要更强的推理能力，用更强的模型重新分派
3. 如果任务太大，拆分为更小的部分
4. 实施阶段为无人值守，只有在反复尝试仍无法通过时才暂停报告状态（最低优先级）

5. 如果同一任务已重试 **2 次**仍失败，或剩余预算不足 5 分钟 → 不再重派，直接进入「降级交付」（见「降级交付与中断兜底」）

**绝不** 忽略上报或在不做任何更改的情况下让同一模型重试。如果实现者说卡住了，说明有什么东西需要改变。

## 子智能体基础设施故障分支（INFRA_FAILED）

**「处理实现者状态」的四种语义状态，描述的是子智能体「自己能给出结论」的情形。基础设施故障没有结论可给——子智能体是被外部打断的，它的沉默既不代表 DONE，也不代表 BLOCKED。** 把这类终止硬塞进 BLOCKED、或者当作「还没跑完」继续等，就是本次事故的直接机制：供应商持续 429 限流时，唯一「合规」的行为是把子智能体一个个派出去，直到控制者自己也被 429 打死——per-task 流程连同规格审查、代码质量审查、最终整体审查、TodoWrite 标记、task.md 复选框同步、完成总结全部落空，而工作区里那份已经被两个独立审查者验证正确的补丁，从头到尾没有任何交付记录。

**基础设施故障是与四种语义状态并列的第五类处置分支，必须在派发前就成文，不得临场发挥。**

### 一、故障信号（出现任一即判定为基础设施故障）

- 子智能体回传含 `API Error` / `Request rejected` / `429` / `rate limit` / `限流` / `overloaded` / `5xx` / `connection reset` / `timeout` 等**外部错误**字样；
- 回传被 harness 标记为 **terminated early**（非子智能体自主结束），或带 `PARTIAL output recovered` / `partial output` / `output truncated` 标记；
- 子智能体在返回任何结构化结论（`STATUS:` / Verdict / 优点-问题-结论）之前就终止；
- 控制者自身收到同类错误（见本节第四点）。

**不要混淆两类终止**：子智能体**主动**返回 `BLOCKED` 并写明原因（缺上下文 / 能力不足 / 任务过大）属于**语义状态**，走「处理实现者状态」的 BLOCKED 分支；子智能体**被外部打断**、没能给出任何结论，才属于**基础设施故障**。

### 二、「terminated early + PARTIAL output recovered」回传格式怎么读

这类回传表示：**子智能体的部分输出已被回收，但会话没有正常结束**。控制者必须按下表解读，**既不得当作「已完成」，也不得当作「什么都没做」**：

| 回收到的内容 | 判定 | 动作 |
| --- | --- | --- |
| 有明确 `STATUS:DONE` 且报告完整 | 产出可信 | 按「接受 DONE 的前置条件」校验后继续流程图下一节点 |
| 有部分产出，无 `STATUS` 或 `STATUS` 不完整 | **产出保全对象** | 先执行「产出保全与交付记录」的登记，再进入有界重试；上限用尽则走降级交付 |
| 完全没有产出 | 无产出可保全 | 进入有界重试；上限用尽则走降级交付 |
| 报告说改了，但工作树里没有对应改动 | 产出不可信 | 记为**关键问题**，**不得**据此放行 |

**任何一种情况，都必须先做「产出保全与交付记录」的登记动作，再决定重试还是收尾。** 顺序反了，重试就可能覆盖掉上一轮已经落盘但没被记录的成果。

### 三、有界重试与退避（不得无限重派）

- **重试上限：同一节点最多重试 2 次**（含首次派发共 3 次尝试），与「同一子智能体最多重试 2 次」「审查迭代 2 轮上限」一致，不额外放宽。
- **退避**：第一次重试前**至少等待 60 秒**，第二次重试前**至少等待 180 秒**。**不得**在同一次响应里连续重派，**不得**用忙等待循环「熬过」等待时间（见「墙钟预算与止损规则」的「4) 等待协议与请求预算」）。
- **重试不得加剧限流**：收到 429 / 限流字样后**立刻停止一切派发**，进入等待；**不得**并行或连续发起多个子智能体去「碰运气」——重试请求与原请求争抢同一份配额，只会更快耗尽。
- **重试时收紧指令**：缩小范围、点名具体文件与具体检查项，避免子智能体重走长链路；长链路是请求量放大的主要来源。
- **重试前先看剩余预算**：剩余预算不足 5 分钟 → **不再重派**，直接走「降级交付与中断兜底」。

### 四、控制者自身受限时的出口（本次事故最关键的缺口）

**控制者被限流 / 被终止，与子智能体是同一个风险源，必须对称处理。** 控制者自身的 API 重试会与子智能体的请求**争抢同一份配额**（实测形态：主控在子审查者死亡后 2 分多钟内连续 5 次重试、间隔 16~38 秒，全部 429，随后主控自己也以 429 终止）。因此：

- 控制者自身收到 429 / 限流时，**不得**用密集重试硬扛；
- 控制者自身被限流时，**唯一合规动作**是：**停止派发 → 立即把当前状态写成交付记录 → 按「降级完成时的输出」模板收尾**（见「降级交付与中断兜底」）。工作区里已有的改动**必须**在收尾报告中逐条列出；
- 「停止派发并收尾」**不违反**任何红线（见「红线」的例外条款）；**继续派发直到会话猝死才是违规路径**。

### 五、与四种语义状态的关系

| 情形 | 判定 | 去向 |
| --- | --- | --- |
| 子智能体主动给出结论（任一四态） | 语义状态 | 「处理实现者状态」 |
| 子智能体被外部打断，无结论 | **INFRA_FAILED** | 本节 |
| 子智能体给出了结论，但结论本身被外部错误打断 | 语义状态优先，**同时**按 INFRA_FAILED 登记交付风险 | 先按语义状态处置，再补交付记录 |
| 控制者自身被限流 / 被终止 | **INFRA_FAILED** | 本节第四点 → 降级交付与中断兜底 |

## 子智能体无响应（挂死）的处置分支

**「子智能体无响应」是独立于四种语义状态、也独立于「terminated early」的一类终止形态，必须在派发前就成文。** 事故形态：控制者派发规格审查子智能体后，该子智能体**既没有回传、也没有留下任何 transcript**（连一条错误原文都没有）；控制者既不能判它 DONE，也不能判它 BLOCKED——「处理实现者状态」的四种语义状态**没有一种能接住这种情况**；于是流程被硬阻塞在「等待审查结论」上，既不能前进也不能收尾，直到运行器在墙钟上限处把会话杀掉：per-task 流程连同后续任务、TodoWrite 标记、task.md 复选框同步、最终报告**全部归零**，而工作区里已经落盘、可能已通过前序审查的改动**没有任何交付记录**。

**关键区分：挂死 ≠ 失败 ≠ 已完成。** 子智能体沉默时三件事同时为真：它没完成、它也没失败、它也没有产出。控制者**不得**据此判定「已通过审查」，**不得**把它当成「实现有问题」去重做实现，**更不得**继续等下去。

### 一、挂死的判定信号（满足任一即判定）

- 到达该次派发的**截止线**（见「墙钟预算与止损规则」的「派发截止线」）仍未回传任何结论；
- 回传为空、只有空白、或只有一句不含任何语义状态 / Verdict 的描述；
- 运行器 / harness 报告该子智能体被取消、被抢占，或「无 transcript / 无产出」；
- 控制者自身在同一等待期已收到 429 / `API Error` / 超时（同一轮外部故障的连带受害者）。

**判定即终止当前等待**：一经判定挂死，**不得**继续等同一轮回传，**不得**改写工作区，**不得**以「也许它还在跑」为理由延长等待，**不得**跳过「产出保全与交付记录」的登记。

### 二、恢复阶梯（有界，且每次重试必须换策略）

挂死走与「子智能体基础设施故障分支」**相同**的重试上限与退避（同一节点最多重试 2 次、含首次共 3 次尝试；第一次重试前等 ≥ 60 秒，第二次前 ≥ 180 秒），此外必须满足：

1. **不得原样重派**。同一个挂死的审查原样再派一次 = 复现同一故障。必须换策略，任选其一：**缩小审查面**（只审一个文件 / 一条验收条目 / 一个具体问题）、**换更快的模型或更短的指令**（点名文件与检查项）、**拆成两次小审查**（把「规格审查 + 代码质量审查」拆成两个更小的审查分别派发）。
2. **重试前必须先登记**（见下条），确认工作树与登记一致；不一致即按「产出不实」处理，**不得**据此放行。
3. **不得**在同一次响应里连续重派，**不得**并行派发去「碰运气」——并发只会更快耗尽配额。
4. **挂死的是实现者时**：重试必须重新分派实现者，**不得**把上一轮的部分实现当成已完成直接交付；**不得**由控制者自己动手补实现（上下文污染，见「如果子智能体失败」）。
5. **挂死的是审查者时**：实现者的改动仍完整落在工作树里，**原样保留**；重试的审查者**只读**，发现问题的唯一出口是回传问题。

### 三、挂死期间的工作区保全（先保全，再重试）

- 判定挂死后、任何重试或收尾动作**之前**，控制者**必须**先把当前工作区状态写进交付记录：`git status --short`、`git diff --stat`，以及「已完成任务清单 + 已落盘改动清单 + 未完成节点 + 故障原文」。
- **挂死时的「故障原文」取法**：没有错误原文就**如实记没有**，**不得**编造、**不得**写成「网络问题」——记录可确证的事实：**节点名、派发时刻、截止线时刻、最后一次观测到的状态（无回传 / 无 transcript）、前序节点是否已回传**。
- **不得**因为「等下要重试」而跳过登记：重试可能再次挂死，甚至直接让会话被取消；登记先做，重试后做。
- **不得**改写工作区来「配合」重试（不得 `git stash` / `git checkout` / `git reset` / `git clean`，见「不得改写工作区」）。

### 四、停止条件（满足任一即停止，不得再派发）

- 同一节点的有界重试已用尽（重试上限 2 次）→ **直接**走「降级交付与中断兜底」，并把该节点写入「未执行的节点清单」；
- 剩余预算 < 5 分钟 → 不再派发任何子智能体；
- 剩余总预算 < 10 分钟且当前节点是最终整体审查 → 跳过，并在报告中注明「最终整体审查未执行（预算不足）」；
- **总预算硬上限临近（剩余 < 2 分钟）**：**立刻**停止一切等待与派发，只做「降级交付与中断兜底」的收尾动作——**在运行器杀掉会话之前**把交付记录写完。**绝不允许「等运行器来杀我」**：被运行器取消时，会话往往在**工具调用仍在途**的状态下直接结束，任何在途状态、未落盘的收尾内容**全部丢失**。

### 五、与既有条款的关系

- 挂死是「基础设施故障」的一种触发情形，因此「子智能体基础设施故障分支」的**有界重试、退避、产出保全登记**与「降级交付与中断兜底」全部适用；本节只补它原文未覆盖的两点：**如何判定沉默**，以及**沉默时如何止损**。
- 本节是「红线」的「跳过流程图中的审查节点」「审查有未解决问题时不得进入下一个任务」的**例外条款之一**：挂死且有界重试用尽时允许走降级交付，但**必须在报告中写明该节点未完成、为什么未完成**。
- 挂死**不得**被当作「审查通过」：未产出审查结论的节点，在报告中一律记为**未执行**，不得计入「已通过审查」。

## 墙钟预算与止损规则

**流程在时间上必须有界。** 没有墙钟预算的多子智能体流水线会吃光整个会话预算：任务做不完、最终总结输出不出来，整个运行被判为失败。因此本批实现必须**先定预算，再派发**。

**1) 确定总预算（首次派发前）**
- 优先使用运行器 / 用户给出的时限（剩余会话时间、作业时限）。
- 没有明示时限时按默认值：**单任务 8 分钟、整批 40 分钟**；记录起点时间戳，后续所有判断以它为准。
- 先数出本批任务数 N，把总预算按 N 分摊到任务，并预留 20% 给最终整体审查与输出报告。

**2) 单任务与派发预算**
- 每个任务上限 = `min(剩余总预算 × 0.4, 该任务分级基准时长)`；分级基准：L0 = 3 分钟 / L1 = 6 分钟 / L2 = 12 分钟 / L3 = 25 分钟。
- 任务累计用时超过上限即视为该任务超时，直接进入「降级交付」，不再开新一轮审查。
- 剩余预算 < 5 分钟时**不再派发任何子智能体**，直接进入「降级交付」。

**3) 单次派发的指令模板（每次都要写进子智能体指令）**
- 写明硬性时限，并要求子智能体自查：
  > 本任务有 **N 分钟**硬性时限。到达时限时立即停止探索，返回当前状态（DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED）与已落盘的改动摘要。
- 写明范围边界：**不要**拉取或比对上游仓库源码、不要访问外网、不要翻阅与本任务无关的文件；信息不足就返回 NEEDS_CONTEXT，由控制者补上下文，而不是自己去找。
- 写明产出形式：改动直接写入工作树文件，不要只给出补丁文本。

- 写明**工作区保全约束**（实现者与审查者**都要**写，缺一不可）：
  - **不得**执行 `git stash` / `git checkout` / `git restore` / `git reset` / `git clean` / `git commit` / `git worktree remove`；**不得**改写任务范围外的任何文件。
  - 审查者**只读**：发现问题的唯一出口是**回传问题**，不是自己动手改代码。
  - 需要「变更前基线」对照时用**只读**方式取（如 `git show HEAD:<path>`、`git diff HEAD -- <path>`），或新建**独立临时 worktree**；**不得**动当前工作树，更不得把工作树整体收起。
  - 理由：审查者一旦执行 `git stash`，就会把已经落盘、且已通过前序审查的改动整体收走；若它随后被限流打断，工作区就既没有补丁、也没有与之一致的交付记录——这是本类事故中最容易被忽略、也最难挽回的一步。

- 写明回归验证关卡（每次都要写，不能省略）：要求实现者按「回归验证关卡」执行——圈定受影响符号 → 全仓库检索引用点（含 `tests/`、`conftest.py`、`<module>.<Name>` 子模块属性形式）→ 运行受影响的既有测试 → 报告真实命令与输出。同时明确告知：「不得新增或修改测试文件」约束的是**写**，**运行既有测试是必须项**；禁止用 `compileall` / import 断言 / 手工片段验证替代。
- 写明审查者的核查项（派发审查子智能体时）：核对实现者报告是否留有受影响既有测试的运行证据与引用点检索结论；核对被删除或改名的符号是否仍被仓库其它位置引用；把「既有测试因本次改动失败」「仍被引用的符号被删除」一律记为**关键问题**。
- 写明**验收条目**（派发实现子智能体时）：把该任务覆盖的矩阵条目原文写进实现者指令——每条含**需求原文引用**与**可执行验收方式**——并明确「返回报告须逐条给出状态（已满足 / 未满足 / 部分满足 / 无法判断）+ 证据（实际命令与输出，或实现位置 + 覆盖它的既有测试）」。**不得**只把 task.md 的任务描述转述给实现者：任务描述正是需求可能被静默降级后的产物，转述它等于把降级固化进实现。
- 写明**覆盖度核对**（派发审查 / 验证子智能体时）：审查者须回到**需求原文**独立核对矩阵条目是否逐条落地，对「不在范围内 / 非目标」条目须核验其原文依据或裁决记录，对每条给出「已满足 / 未满足 / 无法判断 / 与实现冲突」+ 证据，**不得**只给整体结论，**不得**沿用实现者提供的失败名单或条目结论。

- 写明验证门禁的失败处置（派发**验证 / 审查**子智能体时）：要求对**每一条**失败用例给出**变更前基线对照**（同一条命令在变更前后各跑一次），并按 A/B/C 三类分级；明确写出「**不得**把失败解释为『预期行为变化』后放行——只有 issue/spec/design 明确要求、四要件齐全并经升级裁决时才可放行」。同时说明：**指令中不得替你预先定性失败**——你若有怀疑，只能写成「待核查假设 + 要求反证」，不得写成「已知失败，不必修」。

- 写明**同入口同顺序**的基线对照要求（派发**验证 / 审查**子智能体时）：变更前 / 变更后必须是**同一条命令、同一执行入口、同一选择范围与顺序**；若两次的失败用例 ID 不同，或同一用例一次失败一次通过，必须判为**顺序依赖 / 不稳定失败**，用同一入口复跑确认后再分级，并逐条记录复现命令与漂移现象——**不得**只跑变更后就下结论，也**不得**沿用控制者给出的失败名单或结论。

**4) 等待协议与请求预算（防忙等待放大限流）**

- **等待即等待，不得自造忙等待。** 派发子智能体后进入**等待态**，等子智能体的完成通知回传。**禁止**用 `Monitor` + Bash 轮询循环、`sleep` 轮询、或连续发起工具调用来自造「等待」——这类循环会把单会话的请求量放大一个数量级，是触发供应商 429 限流最常见的自伤行为（实测形态：一次派发之后 28.5 分钟内产生 704/870 个助手回合）。
- **轮询上限：最多 2 轮**，每轮间隔 **≥ 60 秒**，每轮只发**一次**状态查询；总等待不得超过该节点的墙钟预算。两轮未回 → 按「子智能体失败」处理（重试上限 2 次），不得无限等待。
- **派发截止线（控制者侧硬约束）**：每次派发前先记下一个**绝对时刻** `deadline = 派发时刻 + min(该节点墙钟预算, 剩余总预算 × 0.4)`。子智能体指令里的「N 分钟硬性时限」是**软约束**（子智能体可能不遵守，也可能已经挂死），**控制者侧的 deadline 才是硬约束**：到达 deadline 仍未回传 → 立即按「子智能体无响应（挂死）的处置分支」判定挂死并止损。deadline 用**绝对时刻**记录，每次等待前用它重算剩余时间；**不得**靠「感觉还早」估算，**不得**因为「快到了」一延再延。
- **沉默即止损（细化上一条「两轮未回 → 按「子智能体失败」处理」）**：判定顺序固定为——**判定挂死 → 登记交付记录 → 有界重试（换策略）→ 重试用尽即降级交付**。**不得**把挂死当作「还没跑完」继续等，**不得**因为它「没有报错」就无限等待。
- **没有状态查询能力时**：若运行环境取不到子智能体的 transcript / 进度事件 / 回传状态，**不得**以「查不到状态」为理由继续等待——按 **deadline** 到点直接判定挂死；也**不得**用 `Monitor` + Bash 轮询去「找」状态（见「请求预算（控制者侧）」）。
- **请求预算（控制者侧）**：控制者自身的每分钟工具调用数**必须**留在个位数量级；同一分钟内**不得**并发发起多个子智能体，也**不得**多次轮询。并发上限恒为 1（与「红线」的「不并行分派」一致）。
- **出现 429 / 限流字样时**：立刻停止全部派发与轮询，按「子智能体基础设施故障分支」的退避与出口处理，**不得**用密集重试硬扛。
- **等待期零输出**：等待期间**不产出**任何「看起来像结论」的中间结论；对外可见的状态一律以「产出保全与交付记录」的交付记录为准。


**5) 审查迭代上限（强制）**
- 每个审查节点（规格审查 / 代码质量审查 / 最终整体审查）最多 **2 轮**「发现问题 → 实现者修复 → 重新审查」。
- 第 2 轮后仍有问题：按严重级分流——关键 / 重要必须在剩余预算内修完；次要问题**记录进最终报告**并允许降级交付，不再开第 3 轮。
- 实现者收到审查意见时只处理审查者指出的问题，不得顺带做无关重构、改名或格式化（这类改动会引出新的审查轮次）。
- 最终整体审查只在剩余预算 ≥ 10 分钟时执行；否则跳过，并在报告中注明「最终整体审查未执行（预算不足）」。

**6) 进度快照**
- 每完成一个任务，在更新 TodoWrite 与 task.md 复选框的同时记录：已完成 N / M、剩余预算。当前状态必须随时可输出，避免被中断时什么都交不出来。

本节同样是对「不跳过图中审查步骤」的受控例外（只在预算不足时减少节点，且必须在报告中写明被跳过的节点与原因）。

## 产出保全与交付记录

**「补丁留在工作区却没有任何交付记录」和「补丁根本没留下」是同一种失败：前者丢的是可追溯性，后者丢的是成果。** 因此本技能要求：**任何时刻、任何节点之后，控制者都必须已经能交出这份交付记录**，而不是等流程全部跑完才临时总结。

### 一、交付记录是什么

交付记录 = **已落盘的成果清单 + 已核验的证据 + 未完成节点的清单**，用于在流程被中断（限流、取消、超时）时**立刻**交出可评估的产物。它**不是**最终完成报告，但**必须**包含最终报告的全部关键事实。

### 二、落盘位置与更新时机

- **落盘**：`codespec/changes/<change-name>/apply-status.md`（与 task.md 同目录）。该文件在**首次派发第一个子智能体之前**创建，此后**每个节点返回后立即更新**（不是批量更新）。
- **不落盘时**：若运行环境不允许写该文件，则必须在**控制者上下文**中维护同等内容，并在每次节点返回后于上下文中显式重述一次（关键事实：已完成任务清单、已落盘改动清单、验证证据、未完成节点、故障原文）。
- **归档前**把该文件删除或并入归档记录（与「验收矩阵的留存」一致），不要让它混进变更产物。
- **每个节点返回后必须更新的内容**：
  1. 已完成任务 N / M（与 TodoWrite、task.md 复选框**同一次**更新，不允许三处不同步）；
  2. **已落盘改动清单**：逐条「文件路径 — 一句话说明 — 来自哪个任务」；
  3. **验证证据**：实际执行的命令与真实输出（通过 / 失败 / 收集错误数）；
  4. **未完成节点**：哪个审查节点没跑、为什么（预算不足 / 基础设施故障 / 未派发）；
  5. **故障原文**：基础设施故障时，把错误原文（429 / `API Error` / terminated early 标记）**原样摘录**，**不得**改写成「网络问题」之类的概括。

**每次派发前必须写入的内容（与「节点返回后更新」同等强制）：**

派发不是「已经完成」，而是一段**结果未知**的时间窗；窗口内会话随时可能被取消。在**派发之前**就把下列内容写进交付记录，让「派发瞬间」本身可被追溯：

1. **节点名与节点类型**（实现者 / 规格审查 / 代码质量审查 / 最终整体审查）、**所属任务**；
2. **派发时刻与该次派发的截止线**（绝对时刻，见「墙钟预算与止损规则」的「派发截止线」）；
3. **派发前的工作区快照**：`git status --short` 与 `git diff --stat` 的真实输出（用于在子智能体挂死 / 被取消时判定工作树里究竟留下了什么）；
4. **前序节点的结论摘要**（已落盘改动清单 + 验证证据 + 未处置的疑虑），确保「已完成的产出」在节点在途期间就已可交；
5. **该节点的产出预期**（应回传什么：状态 / Verdict / 逐条验收结论）与**它挂死时的兜底去向**（有界重试 → 降级交付）。

> 派发前不登记，等于把「窗口期内的成果可交性」押在子智能体会正常返回上——而这正是事故中成果与交付记录双双落空的原因。

### 三、保全动作（任何中断点都要做，且**先于**重试）

- 子智能体返回**部分产出**或**非自愿终止**时，**先**把已落盘改动登记进交付记录，**再**决定重试与否；
- 重试前**必须**确认工作树仍与登记一致（`git status --short` + `git diff --stat`）；不一致即说明产出未真正落盘，按「产出不实」处理，**不得**据此放行；
- 交付记录本身**就是**中断时的兜底产物：**只要它写了，即使会话随后猝死，成果与缺口都已留痕**，不再出现「补丁留在工作区却无任何交付记录」。

### 四、不得改写工作区

- 控制者与**所有**子智能体（含审查者）**不得**执行 `git stash` / `git checkout` / `git restore` / `git reset` / `git clean` / `git commit` / `git worktree remove`；
- 需要变更前基线对照时用只读方式（`git show HEAD:<path>`、`git diff HEAD -- <path>`）或新建独立临时 worktree；
- 审查者**只读**：发现问题的唯一出口是**回传问题**，不是自己动手改；
- 降级交付**不是**回滚：收尾时**不得**为了让工作树看起来干净而 `git stash` / `git reset` / `git checkout`。

## 降级交付与中断兜底

**降级交付是本技能的合法终态，不是失败。** 它在三种情形下触发：剩余预算不足、审查迭代达到上限、**子智能体或控制者遭遇基础设施故障**。第三种是本次事故所属的情形，而此前它**没有任何成文条款**——「降级交付」被反复引用，却从未定义其触发条件、最小交付内容与收尾动作，这正是事故中「无合法出口、只能继续派发直到猝死」的技术来源。

### 一、触发条件（任一成立即触发，不必等流程跑完）

1. 剩余预算不足 5 分钟，或已到总预算上限；
2. 某审查节点的「实现者修复 → 重新审查」达到 2 轮上限；
3. **子智能体或控制者遭遇基础设施故障**（429 / 限流 / API 错误 / 超时 / terminated early），且有界重试已用尽（见「子智能体基础设施故障分支」）；
4. 收到运行器的取消 / 中断信号。
5. **子智能体挂死（无响应）超过该次派发的截止线**，且有界重试已用尽（见「子智能体无响应（挂死）的处置分支」）；
6. 剩余总预算进入**硬上限前的最后 2 分钟**——此时**不等运行器来取消**，直接走本节收尾（见「三、收尾动作」）。

### 二、最小交付内容（降级交付**至少**要交出这些，缺一即降级无效）

1. **已落盘改动清单**（逐条文件路径 + 一句话说明 + 所属任务）；
2. **变更级验证的真实证据**：实际执行的命令与真实输出（通过 N / 失败 M / 收集失败 K）；未运行的测试**逐条列出并写明原因**；
3. **未通过用例**清单（含 A/B/C 分级与处置），无则写「无」；
4. **验收覆盖**：「N/M 条已满足」与未满足条目逐条列出；
5. **未执行的节点清单**：规格审查 / 代码质量审查 / 最终整体审查各自是否执行、为什么没执行（预算不足 / 基础设施故障 / 其它）；
6. **故障证据**：基础设施故障时附**错误原文**与发生时刻；
7. **续做入口**：未完成任务的描述 + 后续可用 `/codespec/apply` 或人工继续的说明。

### 三、收尾动作（顺序固定，不得跳过）

1. **先**更新交付记录（`apply-status.md`），把「已落盘改动清单」与「未完成节点」写全；
2. **再**按「降级完成时的输出」模板输出报告（见下文）；
3. **再**把已落盘改动**留在工作区**——降级交付**不是**回滚；
4. **最后**停止一切派发与轮询。降级交付完成后**不再**发起新的子智能体调用。
5. **再**把交付记录**落盘写完**（已落盘改动清单、验证证据、未完成节点、故障原文、验收覆盖），确保会话**在被取消之前**就已具备可评估的产物。被运行器取消时，会话可能在**工具调用仍在途**的状态下直接结束，届时任何未落盘的收尾内容**取不回来**——所以收尾的最后一步必须是**写盘**，而不是「准备写」。

### 四、与红线的关系

- 触发条件 1 / 2 / 4 命中时，本节是「跳过流程图中的审查节点」「审查有未解决问题时不得进入下一个任务」「带着未修复的问题继续」的**例外条款**（见「红线」的例外条款）；
- 触发条件 3（基础设施故障）命中时，**同样**适用该例外，且**必须**附错误原文作为证据；
- 例外的代价是**显式化**：跳过了哪个节点、为什么、还有什么没验证，全部写进交付记录与报告——**不得**用「基础设施故障」四个字一笔带过。

## 示例工作流

本批的示例工作流不再硬编码于本技能，而是由 `codespec apply-subagent flow --<tdd|test-after|no-test>` 命令一并返回（JSON 的 `example` 字段，或文本输出的「示例工作流」一节）。其默认值为内置默认示例（以内置默认流程为例；自定义流程图同理，按返回的图执行），用户可在 `config.yaml` 的 `subagent-apply.<mode>.example` 中覆盖。

获取后，参照返回的示例理解控制者与子智能体之间的交互节奏（提问 → 实现 → 自审 → 按流程图审查 → 修复 → 重审 → 标记完成），并按本批实际返回的流程图执行。

> 注意：内置默认示例以 `tdd` / `test-after` 风格展示（含测试步骤）。当本批测试策略为 `no-test` 时，实现者不会编写或修改测试文件；示例中的「添加了测试 / N/N 通过」等环节应理解为**运行受影响的既有测试做回归验证**（见「回归验证关卡」）与编译检查、功能自审，而不是「不运行任何测试」。

## 优势

**与手动执行相比：**
- 子智能体严格遵循 task.md 头部标记的测试策略（tdd / test-after / no-test）
- 每个任务全新上下文（不会混淆）
- 并行安全（子智能体不会互相干扰）
- 子智能体可以提问（工作前和工作中都可以）

**效率提升：**
- 无文件读取开销（控制者提供完整文本）
- 控制者精确策划所需上下文
- 子智能体预先获得完整信息
- 问题在工作开始前就被提出（而非工作结束后）

**质量关卡：**
- 自审在交接前发现问题
- 按流程图中的审查节点逐个审查
- 审查循环确保修复确实有效
- 任一审查者报告的每一项问题（关键/重要/次要）都必须完整交给实现子智能体处理，不得摘要、筛选、降级或只选择 bug/关键项
- 规格合规防止过度/不足构建
- 代码质量确保实现良好，验证编译通过
- 回归验证关卡确保既有公共行为未被破坏（no-test 模式同样必做）

**成本：**
- 更多子智能体调用（每个任务需要实现者 + 流程图中的审查者）
- 控制者需要更多准备工作（预先提取所有任务）
- 审查循环增加迭代次数
- 但能及早发现问题（比后期调试更省成本）

## 红线

**绝不：**
- 未经用户明确同意就在 main/master 分支上开始实现
- 跳过流程图中的审查节点
- 带着未修复的问题继续
- 只修“bug/关键”，跳过“重要/次要”
- 回传审查问题时自行摘要、筛选或只挑关键
- 并行分派多个实现子智能体（会冲突）
- 让子智能体读取计划文件（应提供完整文本）
- 跳过场景铺设上下文（子智能体需要理解任务在哪个环节）
- 忽视子智能体的问题（在让它们继续之前先回答）
- 在审查合规性上接受"差不多就行"（审查者发现问题 = 未完成）
- 跳过审查循环（审查者发现问题 = 实现者修复 = 再次审查）
- 让实现者的自审替代正式审查（两者都需要）
- **不按流程图顺序执行审查**（顺序由图中的边决定，顺序错误）
- 在任一审查有未解决问题时就进入下一个任务

- 以 `no-test` 为由跳过运行受影响的既有测试，或把「不得修改测试文件」扩大解释为「禁止运行任何单元测试」
- 删除了仍被仓库其它位置引用的符号（导入、导出、属性），只验证「包级导出仍可导入」就判定兼容性无问题——`pkg.mod.Name` 这类子模块属性访问与 `tests/`、`conftest.py` 中的用法同样是公共行为
- 在没有真实测试运行证据的情况下，把「变更级验证」标记为通过

- 把因本次改动而失败的既有测试用例，以「官方测试补丁会更新」「这是预期行为变化」「量级很小」为由**单方面放过并结案**
- 只跑变更后的测试、没有变更前基线对照，就判定失败用例属于「既有问题」
- 在分派验证 / 审查子智能体的指令中预写「已知预期失败，不用修」这类免责定性，或把控制者的怀疑当结论交给验证者照办

- 把**仓库自带数据 / 环境时效**导致的失败（leap-second / IERS 表过期、证书或时区库过期等）当成 A 类「本次引入」去改生产代码绕开，或为了「验证变绿」去改仓库数据文件、pytest 配置、warning 过滤器
- 只因失败用例**看起来**与本次改动无关就把它从「未通过用例」清单里删掉，或在没有**同入口同顺序**的变更前基线对照前就宣称「既有问题」并结案
- 变更前后基线对照使用了不同的执行入口 / 选择范围 / 顺序（失败用例 ID 会漂移的场景），却据此给出 A / B / C 分级
- 实现者上报 DONE_WITH_CONCERNS（或实现者自己发现的验收偏差）后，不走「修复 → 复审」闭环就放行

- 在子智能体或控制者遭遇 429 / 限流 / API 错误 / 超时后，仍**密集重试或高频重派**（不做退避、不先停派发）
- 用 `Monitor` + Bash 轮询这类**忙等待**充当「等待子智能体」，把单会话请求量放大到触发供应商限流
- 允许**审查者**执行 `git stash` / `git checkout` / `git reset` / `git clean` / `git commit` 或改写工作树（审查者只读，发现问题只回传）
- 子智能体**非自愿终止**（terminated early / PARTIAL output recovered）后，不先登记「已落盘改动清单」就重试或收尾
- 会话被中断 / 因基础设施故障收尾时，没有留下交付记录（`apply-status.md` 或等价的上下文记录），导致工作区里的正确补丁**无任何交付记录**
- 子智能体**无响应**（未回传、无 transcript、无错误原文）时，不按「挂死」判定止损，而是一路等到会话被运行器取消（既不判定、不重试、也不降级交付）
- 子智能体挂死后**原样重派**同一个审查（不换策略），把同一个故障复现第二遍
- 挂死判定后**先重试后登记**（未先把已落盘改动写进交付记录就重试），重试期间再次挂死即导致成果与记录双双落空
- 临近总预算上限时**等运行器来杀**，没有提前收尾并写完交付记录（被取消时在途状态与未落盘内容全部丢失）
- 接受**带警告 / 失败证据的 DONE**（如「既有测试会失败」「官方测试补丁会覆盖」「模块建了但没接线」），不走「验证门禁失败的处置闭环」就进入审查节点

- 把需求原文中的**开放项 / 隐含需求**静默写成「不在范围内 / 非目标」，或仅凭推断（「不重要」「上游大概会更新」「应该没人用」）排除需求原文没有排除的条目
- 只用 task.md 的任务清单反推验收标准，不回溯需求原文（issue / 用户原始请求 / ar.md / spec.md）
- 验收矩阵存在「未落点」条目、或覆盖度未逐条核对（缺「N/M」与未满足条目清单）就进入结项
- 完成报告未列出未通过用例，或在仍有未通过用例时写「变更级验证 ✅」/「所有任务已完成并通过审查」

**例外条款（优先级高于上述红线，且只在命中对应止损条件时生效）：**
- 「跳过流程图中的审查节点」：仅当任务命中「任务体量分级」的 L0 / L1 快速通道，或命中「墙钟预算与止损规则」的预算止损时允许；必须在最终报告中写明跳过了哪些节点、为什么。
- 「带着未修复的问题继续」/「只修 bug/关键，跳过重要/次要」/「回传审查问题时自行摘要、筛选或只挑关键」：仅当审查迭代已达 2 轮上限、且剩余预算不足以修完全部问题时允许——关键 / 重要必须修完，次要项可记录进报告后降级交付；不得借此跳过关键 / 重要项。
- 「跳过审查循环」：每个审查节点最多 2 轮，不是无限循环；第 2 轮之后按上面的严重级分流处理。
- 「让实现者的自审替代正式审查」：仅 L0 任务例外，且实现者自审本身不可省。
- 「审查有未解决问题时不得进入下一个任务」：仅降级交付路径例外，且必须在报告中列出未解决问题。
- 「跳过流程图中的审查节点」/「带着未修复的问题继续」/「审查有未解决问题时不得进入下一个任务」：**子智能体或控制者遭遇基础设施故障**（429 / 限流 / API 错误 / 超时 / terminated early）且有界重试已用尽时，允许按「降级交付与中断兜底」收尾；前提是已写好交付记录（已落盘改动清单 + 未完成节点 + 故障原文）并在报告中逐条列出。
- 同上，「子智能体**无响应 / 挂死**」（未回传、无 transcript、无错误原文）同样适用：到达派发截止线即判定挂死，有界重试用尽后按「降级交付与中断兜底」收尾；前提是已写好交付记录（已落盘改动清单 + 未完成节点 + **挂死事实的如实记录**：节点名、派发时刻、截止线时刻、无回传），并在报告中逐条列出；该节点一律记为**未执行**，不得计入「已通过审查」。
- 以上例外**不适用于**「未经用户同意在 main/master 分支上实现」「并行分派多个实现子智能体」「让子智能体读取计划文件」这几条。

**如果子智能体提问：**
- 清晰完整地回答
- 必要时提供额外上下文
- 不要催促它们进入实现阶段

**如果审查者发现问题：**
- 实现者（同一子智能体）修复
- 审查者再次审查
- 重复直到通过
- 不要跳过重新审查
- **但每个审查节点最多 2 轮**（发现问题 → 修复 → 复审算 1 轮）。第 2 轮仍未通过：关键 / 重要问题在剩余预算内修完，次要问题记录进最终报告并走降级交付，不再开第 3 轮。

**如果子智能体失败：**
- 分派修复子智能体并提供具体指令
- 不要尝试手动修复（上下文污染）
- 同一子智能体最多重试 **2 次**；仍失败则按「降级交付」处理，不要无限重试
- 重试前先看剩余预算；预算不足直接降级交付

**子智能体步骤执行纪律：**
- **严格按步骤顺序** - 实现者子智能体必须严格按计划中的步骤顺序执行，不合并、不跳过、不重排
- **测试策略由计划驱动** - 计划 task.md 头部的 `测试策略` 标记（`tdd` / `test-after` / `no-test`）决定每个任务的步骤形态，必须严格遵循：
  - `tdd`：先写失败测试并确认失败，再写最小实现，再运行测试确认通过
  - `test-after`：先完成功能实现，再编写单元测试覆盖验收场景并运行通过
  - `no-test`：**禁止编写或修改测试文件**（不新增测试、不改写或删除既有测试），**但必须运行受影响的既有测试**做回归验证（见「回归验证关卡」）。「不修改测试文件」是**写约束**，不是**执行禁令**：把它扩大为「禁止运行任何单元测试」会关掉唯一能暴露公共行为破坏的信号
