# 子智能体驱动开发

通过为每个任务分派一个全新的子智能体来执行计划，每个任务完成后按返回流程图中的审查节点进行审查。

**为什么用子智能体：** 你将任务委派给具有隔离上下文的专用智能体。通过精心设计它们的指令和上下文，确保它们专注并成功完成任务。它们不应继承你的会话上下文或历史记录——你要精确构造它们所需的一切。这样也能为你自己保留用于协调工作的上下文。

**核心原则：** 每个任务一个全新子智能体 + 按流程图审查 = 高质量、快速迭代

## 流程

**本批要执行的 per-task 流程与示例工作流由 `codespec apply-subagent flow` 命令按测试模式动态返回，在开始执行任何任务之前第一步获取。**

在开始执行任何任务之前：

1. **确定测试模式并获取本批执行流程（关键，第一步）**：
   - 先读取 task.md 头部的 `测试策略` 标记（`tdd` / `test-after` / `no-test`）；未找到时默认 `tdd`。
   - 按该模式运行（缺省 flag 时命令默认按 `tdd` 返回）：
   ```bash
   codespec apply-subagent flow --tdd        # 或 --test-after / --no-test
   ```
   - 返回的 dot 流程图即本批实际要执行的 per-task 流程；返回的 example 即本批示例工作流（见下文「示例工作流」一节）。
   - 严格按返回图中的节点与边执行：只为图中出现的 agent 分派子智能体；不添加图中没有的审查步骤，也不跳过图中有的审查步骤。
2. 读取 spec.md, design.md 和 task.md，建立全局需求理解。
   - **给每个任务定级**（见「任务分级与执行预算」），并把级别写进分派指令。
   - **分派指令必须自带完成条件**：要改的文件、要覆盖的场景、验收用的具体命令与期望结果、允许的时间上限。子智能体**不读** task.md / spec.md / design.md，也不联网。
   - **明确禁止子智能体联网**：本环境通常无外网，拉取上游仓库 / PR / issue 原文的请求会被拦截并白等数分钟；实现与审查只能依据分派指令给出的文本与本地工作区。确实无法从本地确定的上游行为，作为**显式问题**写进返回结果，而不是去抓网。
   - **要求实现者先给结论再给证据**：返回时先给「改了哪些文件 / 每个文件的改动要点 / 自审发现的问题 / 未能验证的点」，控制者据此决定是否进入审查节点。
3. 提取所有任务的完整文本与上下文，创建 TodoWrite：**每个任务一个条目**（任务内的实现与图中该任务的各审查节点都是该条目的子步骤，**不要**为子步骤创建条目）。

  **TodoWrite 纪律（关键）：**
  - 在开始实现前，**必须**用 Todo 为所有未完成任务创建条目(**只跟踪任务，不要跟踪子步骤**)
  - 每完成一个任务后，**立即**将其标记为 completed
  - 不要批量标记——完成一个标记一个
  - TodoWrite 是 continuation enforcer 判断进度的基础，不遵守 = 系统误判

  **task.md 复选框同步（关键）：**
  - 每完成一个任务后，**同时**用 Edit 工具更新 `task.md` 文件中的任务复选框
  - 将对应任务的 `### [ ]` 改为 `### [x]`
  - task.md 路径：`codespec/changes/<change-name>/task.md`
  - 确保 task.md 中的复选框状态与 TodoWrite 完成进度保持一致


  **任务完成登记与进度落盘（关键）：**
  - 流程图把「标记完成」放在实现 + 全部审查之后。一旦进程在审查前被终止，「代码已改并通过测试」就无处登记——**必须把实现完成单独登记一次**：
    1. 用 `git status` / `git diff` 确认改动已落盘
    2. 按 task.md 头部的 `测试策略` 运行该任务相关的测试，记录通过数
    3. **立即**把 task.md 中该任务的 `### [ ]` 改为 `### [x]`，并在 TodoWrite 中标记 completed
  - 登记不是新增流程节点，也不改变流程图的执行顺序；它只把已经发生的事实写下来，审查节点仍必须按图执行。
  - 该任务的审查节点尚未执行时，在 task.md 该任务下追加一行 `> **待审查：** spec-reviewer / code-quality-reviewer`（或流程图中的实际审查节点）。**绝不**把「实现已完成、审查未完成」记成「未开始」。
  - **恢复会话时**：先读 task.md 复选框、`> **待审查：**` 行与 `git diff`，复原已完成到哪一步，不要重做已落盘的任务。

  **验收门禁（关键）：**
  - 把任何任务记为完成之前，先把该任务对应到**可执行的验收检查**（具体命令 + 期望结果）并逐条跑过。流程图里没有验收节点时，**由控制者自己执行**这一步——验收是控制者的义务，不是可选项。这是控制者的自查步骤，不新增审查子智能体，不违反「只为图中出现的 agent 分派子智能体」。
  - **需求不得静默丢弃**：原始 issue / AR / spec 提出的每一条需求，都要能在 spec.md 或 task.md 中找到对应项。某条需求若被判定为暂不实现，必须**显式写进 spec.md 并在最终报告中列出**，禁止在实现阶段用「不加入 X」的方式悄悄删除。
  - **既有失败用例不得当作「预期内」带病收尾**：若本次改动涉及的既有用例失败，必须当场判定是**改动引入的回归**还是**改动前就存在的基线失败**——用 `git stash` / `git stash pop` 对比改动前后的运行结果确认。属于回归的必须修复；属于基线失败的要在报告中写明并附对比证据。
  - 验收门禁不通过时，不得输出「实现完成」。

## 任务分级与执行预算（关键：动手前先算账）

同一批任务的变更面可能相差一个数量级。若所有任务都套用「实现者 → 规格审查 → 代码质量审查 → 返修重审」并完全串行，子智能体调用数会被放大到 **3N+1** 次，足以吃掉整个会话预算——最常见的失败不是补丁写错，而是**流程没跑完、会话被硬性中断**。

**1. 分级（按变更面，不按任务数量）：**

| 级别 | 判据 | 实现者 | 每个审查者的返修轮次上限 | 预计耗时 |
| --- | --- | --- | --- | --- |
| S | 单文件、约 ≤30 行、无 API/Schema 契约变更、无新依赖 | 1 次派发 | **1 轮** | 约 10 分钟 |
| M | 2–3 个文件、局部 API 变更 | 1 次派发 | **2 轮** | 约 20 分钟 |
| L | 跨模块、Schema/API 契约变更、新依赖或迁移 | 1 次派发 | **2 轮** | 约 40 分钟以上 |

- 分级只决定**返修轮次上限**、**实现者的准备深度**与**预算裁剪顺序**；**不新增流程图以外的节点，也不减少流程图要求的节点**。
- **返修轮次上限是硬上限**：达到上限仍未通过时，把该审查节点记为「待审查」，把未修复项逐条写进降级报告再继续下一个任务，**不得**无限循环「实现 → 修复 → 复审」。
- 未修复项**不得静默丢弃**：要么修复，要么登记为「待审查 / 未修复」并附原因。

**2. 预算核算（派发前必做）：**

1. 统计任务数 N 与各级别任务数，算出**预计子智能体调用数**：`N（实现者）+ 审查节点数 × N + 1（整体审查）`；默认流程即 **3N+1**。
2. 估算本批总耗时 `Σ（各级别预计耗时）`，与**会话剩余时间**比较。
3. **剩余时间不足以跑完预计流程时**：立刻按下面的「预算裁剪」裁剪，并从一开始就按裁剪后的计划执行——**不要先跑满再发现没时间**。
4. 每个任务派发前再核对一次剩余时间；剩余时间低于该任务剩余节点所需时间时**不要派发**，直接进入降级收尾。

**3. 预算裁剪顺序（仅在剩余时间不足时启用，按此顺序砍）：**

1. 砍**整体最终审查**（最后一个节点）→ 记为「待审查」。
2. 砍**代码质量审查** → 降级为实现者自审 + 控制者抽查（`git diff` + 编译/测试），记为「待审查」。
3. 砍**规格审查** → 仅当改动为 S 级且实现者自审通过时允许，记为「待审查」。
4. 每层被裁剪的节点都要写进 task.md 与最终报告的「待审查」清单——**裁剪不等于省略**。

> 被裁剪的节点一律以「待审查」形式保留登记；恢复会话时补跑，**不要重做已落盘的实现**。
> 本节是本技能中**唯一**允许不把流程图完整跑完的条款；其余条款一律照旧。

**开工前 30 秒检查（缺一项就不要开始派发）：**
- [ ] 每个任务已定级（S / M / L）
- [ ] 预计子智能体调用数（3N+1）与总耗时已估算，并与剩余时间比较过
- [ ] 若时间不足：已确定按什么顺序裁剪、哪些节点会被记为「待审查」

## 处理实现者状态

实现子智能体报告四种状态之一。根据每种状态进行相应处理：此外还有第五种情况——子智能体在返回状态之前被外部运行时中断（429 限流、超时、5xx、进程被杀、会话被取消），它既不是 DONE 也不是 BLOCKED，按下文「INTERRUPTED（传输层中断）」分支处理。

**DONE：** 进入流程图中的下一个审查节点。

**DONE_WITH_CONCERNS：** 实现者完成了工作但标记了疑虑。在继续之前阅读这些疑虑。如果疑虑涉及正确性或范围，在审查前解决。如果只是观察性说明（如"这个文件越来越大了"），记录下来并继续审查。

**NEEDS_CONTEXT：** 实现者需要未提供的信息。提供缺失的上下文并重新分派。

**BLOCKED：** 实现者无法完成任务。评估阻塞原因：
1. 如果是上下文问题，提供更多上下文并用同一模型重新分派
2. 如果任务需要更强的推理能力，用更强的模型重新分派
3. 如果任务太大，拆分为更小的部分
4. 实施阶段为无人值守，只有在反复尝试仍无法通过时才暂停报告状态（最低优先级）


> **先分辨语义阻塞与基础设施故障：** 429 限流 / 超时 / 5xx / 进程被 SIGTERM / 会话被取消属于**传输层故障**，不属于上面 1–3 项：不要换模型、不要拆任务、不要把任务记成 BLOCKED 终态。按下面的 INTERRUPTED 分支处理。

**INTERRUPTED（传输层中断，第五态）：** 子智能体在返回状态之前被外部运行时终止（供应商限流、网关超时、5xx、进程被杀、会话被取消）。这不是实现者的语义失败，必须单独处理：

1. **先查工作区，再谈重试**：用 `git status` / `git diff` 确认改动是否已落盘。已落盘就**不要重做该任务**——把落盘内容当作候选实现，接着做验证与审查。
2. **退避重试，而不是换模型**：对同一任务用**同一模型**按指数退避重试（起始约 60s，逐次翻倍，单次上限约 5 分钟，最多 3 次）。换更强模型对限流无效，只会额外消耗配额。
3. **重试时补齐续做上下文**：分派指令中写明「上次执行到哪一步、已落盘哪些文件、还差什么」，避免子智能体从头重做。
4. **区分「部分完成」与「未开始」**：改动只落盘了一半（缺文件、缺测试、缺步骤）时按 NEEDS_CONTEXT 处理——补齐上下文后只重跑缺口。
5. **重试到上限仍失败**：不得静默丢弃。转入「会话预算与降级收尾」，输出已落盘内容、未完成项与恢复方式。

**绝不** 忽略上报或在不做任何更改的情况下让同一模型重试。如果实现者说卡住了，说明有什么东西需要改变。


> **例外（传输层故障）：** 当失败原因是 429 限流 / 超时 / 5xx 等外部基础设施故障时，**用同一模型退避重试就是「做了某些更改」的正解**，不违反本条红线。此处「改变」指重试参数与恢复上下文（续做点、已落盘文件清单、重试次数上限），不是换模型。只有语义性失败（BLOCKED / NEEDS_CONTEXT）才要求你换模型或拆分任务。

## 示例工作流

本批的示例工作流不再硬编码于本技能，而是由 `codespec apply-subagent flow --<tdd|test-after|no-test>` 命令一并返回（JSON 的 `example` 字段，或文本输出的「示例工作流」一节）。其默认值为内置默认示例（以内置默认流程为例；自定义流程图同理，按返回的图执行），用户可在 `config.yaml` 的 `subagent-apply.<mode>.example` 中覆盖。

获取后，参照返回的示例理解控制者与子智能体之间的交互节奏（提问 → 实现 → 自审 → 按流程图审查 → 修复 → 重审 → 标记完成），并按本批实际返回的流程图执行。

> 注意：内置默认示例以 `tdd` / `test-after` 风格展示（含测试步骤）。当本批测试策略为 `no-test` 时，实现者不会编写或运行任何单元测试，示例中的"添加了测试 / N/N 通过"等环节应理解为编译检查与功能自审，而非单元测试。

## 等待子智能体：一次阻塞等待，不要轮询（关键）

控制者**最容易被浪费掉的时间**不是子智能体干活，而是**等待方式**。反复 Monitor 子智能体 transcript、反复 `git diff` 查进度、monitor 超时过期后重复 re-arm 同一个目标、`TaskStop` 探一探「还在不在」、`sleep` 轮询——这些都会把控制者自己的上下文与轮次吃光，让真正的实现与审查没时间跑。

**正确做法：**
1. 派发后**只等一次完成通知**（子智能体完成 / 失败会回传结果），不要主动去翻它的 transcript、文件或状态列表。
2. 需要长等待时用**一次长时阻塞等待**（把等待放在工具自身的 timeout 里），**不要**用「短等待 + 检查 + 再短等待」的循环。
3. `TaskStop` 只用于**确认要中止**该子智能体，**不得**当作「查状态」的手段。
4. monitor 类工具超时过期后**不要重复 re-arm** 同一个目标，改为等完成通知。
5. **确需轮询时**：最多 3 次、间隔 ≥ 60 秒、每次只问一个问题（「是否仍在运行」），且轮询本身不产生新的实现指令。
6. **控制者自身的工具调用总数**建议控制在几十次量级（超过约 60 次基本说明在轮询或重复读文件）——控制者的上下文要留给「分派指令」与「决策」。
7. 子智能体提问时会主动回传；**不要**用轮询去「等它问」，收到提问再回答即可。

## 优势

**与手动执行相比：**
- 子智能体严格遵循 task.md 头部标记的测试策略（tdd / test-after / no-test）
- 每个任务全新上下文（不会混淆）
- 并行安全（子智能体不会互相干扰）
- 子智能体可以提问（工作前和工作中都可以）

**效率提升：**
- 无文件读取开销（控制者提供完整文本）
- 控制者精确策划所需上下文
- 子智能体预先获得完整信息
- 问题在工作开始前就被提出（而非工作结束后）

**质量关卡：**
- 自审在交接前发现问题
- 按流程图中的审查节点逐个审查
- 审查循环确保修复确实有效
- 任一审查者报告的每一项问题（关键/重要/次要）都必须完整交给实现子智能体处理，不得摘要、筛选、降级或只选择 bug/关键项
- 规格合规防止过度/不足构建
- 代码质量确保实现良好，验证编译通过

**成本：**
- 更多子智能体调用（每个任务需要实现者 + 流程图中的审查者）
- 控制者需要更多准备工作（预先提取所有任务）
- 审查循环增加迭代次数
- 但能及早发现问题（比后期调试更省成本）

## 红线

**绝不：**
- 未经用户明确同意就在 main/master 分支上开始实现
- 跳过流程图中的审查节点（唯一例外见「任务分级与执行预算」的预算裁剪：剩余时间不足时按序裁剪，并把被裁剪节点登记为「待审查」）
- 带着未修复的问题继续
- 只修“bug/关键”，跳过“重要/次要”
- 回传审查问题时自行摘要、筛选或只挑关键
- 并行分派多个实现子智能体（会冲突）
- 让子智能体读取计划文件（应提供完整文本）
- 跳过场景铺设上下文（子智能体需要理解任务在哪个环节）
- 忽视子智能体的问题（在让它们继续之前先回答）
- 在审查合规性上接受"差不多就行"（审查者发现问题 = 未完成）
- 跳过审查循环（审查者发现问题 = 实现者修复 = 再次审查）
- 让实现者的自审替代正式审查（两者都需要）
- **不按流程图顺序执行审查**（顺序由图中的边决定，顺序错误）
- 在任一审查有未解决问题时就进入下一个任务（例外：已达该审查者的返修轮次上限、且继续重审会挤掉剩余任务的时间时，把未修复项逐条登记为「待审查 / 未修复」后继续，不得静默丢弃）

**如果子智能体提问：**
- 清晰完整地回答
- 必要时提供额外上下文
- 不要催促它们进入实现阶段

**如果审查者发现问题：**
- 实现者（同一子智能体）修复
- 审查者再次审查
- 重复直到通过——但**每个审查者最多 2 轮返修（S 级任务 1 轮）**；达上限仍未通过时按「任务分级与执行预算」记为「待审查」并写进报告，不得无限循环
- 不要跳过重新审查

**如果子智能体失败：**
- 分派修复子智能体并提供具体指令
- 不要尝试手动修复（上下文污染）

- **若失败原因是传输层中断（429 / 超时 / 5xx / 进程被杀 / 会话被取消）**：不要按「重新分派一个修复子智能体」处理——先 `git status` / `git diff` 确认改动是否已落盘，已落盘就**接着验证与审查**，只重跑没做完的步骤
- 重试的分派指令必须写明续做点（已落盘的文件、已完成的步骤、剩余步骤），并要求子智能体先确认工作区现状再动手
- 同一任务退避重试超过 3 次仍失败：转入「会话预算与降级收尾」，输出已落盘内容与未完成项，**不得**静默丢弃

**子智能体步骤执行纪律：**
- **严格按步骤顺序** - 实现者子智能体必须严格按计划中的步骤顺序执行，不合并、不跳过、不重排
- **测试策略由计划驱动** - 计划 task.md 头部的 `测试策略` 标记（`tdd` / `test-after` / `no-test`）决定每个任务的步骤形态，必须严格遵循：
  - `tdd`：先写失败测试并确认失败，再写最小实现，再运行测试确认通过
  - `test-after`：先完成功能实现，再编写单元测试覆盖验收场景并运行通过
  - `no-test`：仅实现功能代码并编译检查，**禁止**编写或运行任何单元测试


## 会话预算与降级收尾

**硬性规则：每次会话都必须以一份报告结束。** 「实现完成」/「降级完成」/「实现暂停」三选一；即使只完成了部分任务、即使审查节点没跑完、即使下一步就会被 SIGTERM 打断，**也必须先输出报告**。绝不出现「补丁已落盘、会话却没有任何交付记录」的情况——没有报告的会话等于失败。

**时间自检（每派发一个子智能体之前都要做）：**
1. 记下本批的**时间预算**（会话总时长上限）、**已用时间**与**剩余时间**。
2. 剩余时间是否够跑完该任务**剩余的全部节点**（实现 + 尚未执行的审查 + 返修）？不够就**不要派发**，按「任务分级与执行预算」的预算裁剪降级，并进入收尾。
3. 剩余时间不够跑整体最终审查时，直接跳过该节点并记为「待审查」。
4. 把时间限制写进**每一次**实现者 / 审查者分派指令：「在 X 分钟内给出结论」；超时就按「传输层中断」处理（见「处理实现者状态」）。

会话可能被外部运行时随时终止（SIGTERM、会话取消、限流）。**不要让一次瞬时故障毁掉整批已完成的工作。**

**每个任务的重试预算：** 同一任务的实现子智能体最多重试 3 次（退避约 60s → 2min → 4min，单次上限约 5min）；审查子智能体同样适用。重试次数用完仍未通过，不要继续无限重试——转入下面的降级收尾。

**每完成一个任务立刻落盘进度：**
1. `git status` / `git diff` 确认改动在磁盘上
2. 运行该任务相关的测试并记录输出
3. 立刻更新 task.md 复选框 + TodoWrite（不要攒到最后一起写）

**预算耗尽或被中断时的降级收尾（按此顺序）：**
1. 停止分派新的子智能体
2. 把已落盘且已验证的任务在 task.md 中标记完成（见「任务完成登记与进度落盘」）
3. 输出「降级完成」报告：列出已完成并有测试证据的任务、已落盘但未审查的任务、尚未开始的任务
4. 写明恢复方式：重新执行本变更时先读 task.md 复选框与 `git diff`，**不要重做已落盘的改动**，直接补跑未执行的审查节点

**绝不** 为了「跑完流程」在一个已落盘、已验证的任务上重复分派实现子智能体——那会覆盖正确实现并浪费预算。
