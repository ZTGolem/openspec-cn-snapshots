# 子智能体驱动开发

通过为每个任务分派一个全新的子智能体来执行计划，每个任务完成后按返回流程图中的审查节点进行审查。

**为什么用子智能体：** 你将任务委派给具有隔离上下文的专用智能体。通过精心设计它们的指令和上下文，确保它们专注并成功完成任务。它们不应继承你的会话上下文或历史记录——你要精确构造它们所需的一切。这样也能为你自己保留用于协调工作的上下文。

**核心原则：** 每个任务一个全新子智能体 + 按流程图审查 = 高质量、快速迭代

## 流程

**本批要执行的 per-task 流程与示例工作流由 `codespec apply-subagent flow` 命令按测试模式动态返回，在开始执行任何任务之前第一步获取。**

在开始执行任何任务之前：

1. **确定测试模式并获取本批执行流程（关键，第一步）**：
   - 先读取 task.md 头部的 `测试策略` 标记（`tdd` / `test-after` / `no-test`）；未找到时默认 `tdd`。
   - 按该模式运行（缺省 flag 时命令默认按 `tdd` 返回）：
   ```bash
   codespec apply-subagent flow --tdd        # 或 --test-after / --no-test
   ```
   - 返回的 dot 流程图即本批实际要执行的 per-task 流程；返回的 example 即本批示例工作流（见下文「示例工作流」一节）。
   - 严格按返回图中的节点与边执行：只为图中出现的 agent 分派子智能体；不添加图中没有的审查步骤，也不跳过图中有的审查步骤。
   - **唯一例外（关键）：** 《验收与回归门禁》是返回图中**可能缺失、但必须补做**的门禁节点——若返回的流程图里没有等价节点（例如 `no-test` 分支只有「实现 → 审查」而无验证节点），控制者必须自行补上并据此阻断交付；**不得**以「图中没有该步骤」为由跳过。
2. 读取 spec.md, design.md 和 task.md，建立全局需求理解。
   - **同时产出「验收清单」（关键）：** 把 spec.md 中的每条需求、每个 WHEN/THEN 场景逐条落成一条**可执行验收项**（写明验证方式 + 可观测的预期结果）。清单只保留在控制者上下文中，不写入仓库文件、不新增 Todo 条目（TodoWrite 仍只跟踪任务）。
   - 无法落成可执行验收项的需求（依赖不可获得的外部信息、需求之间自相矛盾等）：**不得静默跳过**，必须写明原因并升级为阻塞项上报。
3. 提取所有任务的完整文本与上下文，创建 TodoWrite：**每个任务一个条目**（任务内的实现与图中该任务的各审查节点都是该条目的子步骤，**不要**为子步骤创建条目）。

  **TodoWrite 纪律（关键）：**
  - 在开始实现前，**必须**用 Todo 为所有未完成任务创建条目(**只跟踪任务，不要跟踪子步骤**)
  - 每完成一个任务后，**立即**将其标记为 completed
  - 不要批量标记——完成一个标记一个
  - TodoWrite 是 continuation enforcer 判断进度的基础，不遵守 = 系统误判

  **task.md 复选框同步（关键）：**
  - 每完成一个任务后，**同时**用 Edit 工具更新 `task.md` 文件中的任务复选框
  - 将对应任务的 `### [ ]` 改为 `### [x]`
  - task.md 路径：`codespec/changes/<change-name>/task.md`
  - 确保 task.md 中的复选框状态与 TodoWrite 完成进度保持一致

## 验收与回归门禁（no-test 分支必做）

**核心原则：`no-test` 约束的是「本次新增的测试」，不是「免于验证」。**

`no-test` 的含义是：不得编写新的单元测试，也不得把测试步骤写进 task.md 的实现步骤。它**从不**豁免下面两件事：

1. **需求验收**——本次变更是否真的实现了 spec.md 里的需求。
2. **既有行为回归**——本次变更是否破坏了仓库中已有的行为。

仓库里**已经存在**的测试文件不是「本次新增的测试」；运行它们做回归验证不属于「编写测试」，因此不受 `no-test` 约束。**编译检查通过不等于变更正确**：编译只保证语法与类型成立，不保证语义没有回退。

本节门禁是**控制者**的职责，不是某个实现子智能体的任务步骤，因此**不需要**写进 task.md，也不与「测试策略由计划驱动」冲突。

### 门禁 A：需求验收（阻断式）

在把任何任务标记为 completed 之前：

1. 取出《流程》第 2 步产出的「验收清单」，逐条执行每一项验收。
2. 每项必须留下**本次会话内新产生**的证据（命令 + 实际输出 + 退出码）。「应该能过」「之前跑过」「推断没问题」「子代理说通过了」一律不算证据。
3. 任何一项失败 → **阻塞**：交回同一实现子智能体修复，重跑该验收项与全部已通过的验收项，直到全绿。
4. 全部验收项通过后，才允许把该任务标记为 completed。

### 门禁 B：既有行为回归（阻断式）

在**首次改动某个模块之前**，先记录该模块既有测试的**基线**：运行结果（命令 + 退出码 + 通过数/失败数）。基线用于区分「仓库既有失败」与「本次引入的失败」。

在把任务标记为 completed 之前：

1. 对照本次改动的 diff，确定受影响的模块与文件。
2. 找出覆盖这些模块的**既有**测试文件（仓库中已存在的测试），运行受影响范围的既有测试。
3. 记录：命令、退出码、通过数/失败数，以及与基线的差异。
4. 判定：
   - 出现**基线中没有的新失败** → **阻塞**：这是本次变更引入的回归，必须修复后重跑。
   - 基线中已存在的失败 → 如实记录，不计入本次变更，但必须在最终报告中完整列出。
   - 受影响范围全部通过 → 门禁 B 通过。
5. **不得**在未运行的情况下，把受影响既有用例的失败归类为「预期内」「旧行为被移除」「官方测试补丁会更新」「下游会适配」。这些是**未经运行的假设**，不是证据。

### 门禁 C：交付前判定（阻断式）

向用户报告完成之前，控制者必须逐条确认并留痕：

- [ ] 验收清单每一项都有本次会话内的新证据，且全部通过
- [ ] 受影响范围的既有测试已运行，命令与结果已记录
- [ ] 与基线对比后，本次引入的新失败为 0（基线既有失败已如实列出）
- [ ] 实现者上报的所有疑虑已逐条结清；涉及行为破坏/兼容性的疑虑已作为**阻塞项**处理完毕（见《处理实现者状态》）
- [ ] 计划或任务描述里预先写好的「预期失败」「外部会补上」「官方会更新」等结论，都已用本次运行证据核对过；核对不成立的已撤销，并按阻塞处理
- [ ] 计划阶段未确认的前提（例如「仓库当前处于某个发布阶段」）在本次会话内被重新核实，或已作为阻塞项上报

任一项不满足 → **不得报告完成**，先修复、再重跑门禁。

### 门禁与流程图、审查节点的关系

- 返回的流程图中若已包含等价节点（编译检查、变更级验证、change-verifier 等），按图执行即可；但门禁 A/B/C 仍须由**本次会话内的新证据**满足，不得复用历史结果或他人转述的结果。
- 返回的流程图中若**不含**等价节点（如 `no-test` 分支），控制者必须自行补上门禁 A/B/C。这是《流程》第 1 步「不添加图中没有的审查步骤」的**唯一例外**。
- 门禁不新增 Todo 条目：它挂在每个任务条目的完成判定上，而不是独立的跟踪项。

## 处理实现者状态

实现子智能体报告四种状态之一。根据每种状态进行相应处理：

**DONE：** 进入流程图中的下一个审查节点。

**DONE_WITH_CONCERNS：** 实现者完成了工作但标记了疑虑。在继续之前**逐条**阅读这些疑虑，**先分类、再决定是否继续**：

- **阻塞类**（涉及正确性、范围、兼容性、破坏性变更、既有行为可能失效、既有测试可能失败）：**不得降级**——不得记作「附带收益」，不得归入观察性说明，不得以「预期内」带过。逐条核实：核实属实且尚未解决的，就是**阻塞项**，按《验收与回归门禁》补证据、修实现、重跑门禁，直到结清；核实不属实的，写明依据再继续。
- **观察类**（与本次变更的行为无关，如「这个文件越来越大了」）：记录下来并继续审查。

**NEEDS_CONTEXT：** 实现者需要未提供的信息。提供缺失的上下文并重新分派。

**BLOCKED：** 实现者无法完成任务。评估阻塞原因：
1. 如果是上下文问题，提供更多上下文并用同一模型重新分派
2. 如果任务需要更强的推理能力，用更强的模型重新分派
3. 如果任务太大，拆分为更小的部分
4. 实施阶段为无人值守，只有在反复尝试仍无法通过时才暂停报告状态（最低优先级）

**绝不** 忽略上报或在不做任何更改的情况下让同一模型重试。如果实现者说卡住了，说明有什么东西需要改变。

## 示例工作流

本批的示例工作流不再硬编码于本技能，而是由 `codespec apply-subagent flow --<tdd|test-after|no-test>` 命令一并返回（JSON 的 `example` 字段，或文本输出的「示例工作流」一节）。其默认值为内置默认示例（以内置默认流程为例；自定义流程图同理，按返回的图执行），用户可在 `config.yaml` 的 `subagent-apply.<mode>.example` 中覆盖。

获取后，参照返回的示例理解控制者与子智能体之间的交互节奏（提问 → 实现 → 自审 → 按流程图审查 → 修复 → 重审 → 标记完成），并按本批实际返回的流程图执行。

> 注意：内置默认示例以 `tdd` / `test-after` 风格展示（含测试步骤）。当本批测试策略为 `no-test` 时，示例中的「添加了测试 / N/N 通过」等环节应理解为**控制者**执行的《验收与回归门禁》（需求验收 + 既有行为回归），**不是**让实现者编写新的单元测试。实现者在 `no-test` 下仍然不写新测试；运行仓库中既有的测试属于回归验证，不受此限。

## 优势

**与手动执行相比：**
- 子智能体严格遵循 task.md 头部标记的测试策略（tdd / test-after / no-test）
- 每个任务全新上下文（不会混淆）
- 并行安全（子智能体不会互相干扰）
- 子智能体可以提问（工作前和工作中都可以）

**效率提升：**
- 无文件读取开销（控制者提供完整文本）
- 控制者精确策划所需上下文
- 子智能体预先获得完整信息
- 问题在工作开始前就被提出（而非工作结束后）

**质量关卡：**
- 自审在交接前发现问题
- 按流程图中的审查节点逐个审查
- 审查循环确保修复确实有效
- 任一审查者报告的每一项问题（关键/重要/次要）都必须完整交给实现子智能体处理，不得摘要、筛选、降级或只选择 bug/关键项
- 规格合规防止过度/不足构建
- 代码质量确保实现良好，验证编译通过

**成本：**
- 更多子智能体调用（每个任务需要实现者 + 流程图中的审查者）
- 控制者需要更多准备工作（预先提取所有任务）
- 审查循环增加迭代次数
- 但能及早发现问题（比后期调试更省成本）

## 红线

**绝不：**
- 未经用户明确同意就在 main/master 分支上开始实现
- 跳过流程图中的审查节点
- 带着未修复的问题继续
- 只修“bug/关键”，跳过“重要/次要”
- 回传审查问题时自行摘要、筛选或只挑关键
- 并行分派多个实现子智能体（会冲突）
- 让子智能体读取计划文件（应提供完整文本）
- 跳过场景铺设上下文（子智能体需要理解任务在哪个环节）
- 忽视子智能体的问题（在让它们继续之前先回答）
- 在审查合规性上接受"差不多就行"（审查者发现问题 = 未完成）
- 跳过审查循环（审查者发现问题 = 实现者修复 = 再次审查）
- 让实现者的自审替代正式审查（两者都需要）
- **不按流程图顺序执行审查**（顺序由图中的边决定，顺序错误）
- 在任一审查有未解决问题时就进入下一个任务
- 在任一审查有未解决问题时就进入下一个任务
- 在 `no-test` 模式下跳过《验收与回归门禁》的需求验收或既有测试运行
- 把受影响既有用例的失败标为「预期内」「旧行为被移除」「官方测试补丁会更新」，而未用本次运行证据核实
- 把实现者提出的行为破坏/兼容性疑虑降级为「附带收益」或观察性说明
- 复用历史结果或他人转述的运行结果当作本次的验证证据

**如果子智能体提问：**
- 清晰完整地回答
- 必要时提供额外上下文
- 不要催促它们进入实现阶段

**如果审查者发现问题：**
- 实现者（同一子智能体）修复
- 审查者再次审查
- 重复直到通过
- 不要跳过重新审查

**如果子智能体失败：**
- 分派修复子智能体并提供具体指令
- 不要尝试手动修复（上下文污染）

**子智能体步骤执行纪律：**
- **严格按步骤顺序** - 实现者子智能体必须严格按计划中的步骤顺序执行，不合并、不跳过、不重排
- **测试策略由计划驱动** - 计划 task.md 头部的 `测试策略` 标记（`tdd` / `test-after` / `no-test`）决定每个任务的步骤形态，必须严格遵循：
  - `tdd`：先写失败测试并确认失败，再写最小实现，再运行测试确认通过
  - `test-after`：先完成功能实现，再编写单元测试覆盖验收场景并运行通过
  - `no-test`：仅实现功能代码并编译检查，**禁止编写新的单元测试**、禁止把测试步骤写进 task.md；但**不豁免**控制者的《验收与回归门禁》——需求验收与既有行为回归照常执行（见《验收与回归门禁（no-test 分支必做）》）。编译检查通过不等于需求达成，也不等于没有回归。
