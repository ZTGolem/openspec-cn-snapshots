# 子智能体驱动开发

通过为每个任务分派一个全新的子智能体来执行计划，每个任务完成后按返回流程图中的审查节点进行审查。

**为什么用子智能体：** 你将任务委派给具有隔离上下文的专用智能体。通过精心设计它们的指令和上下文，确保它们专注并成功完成任务。它们不应继承你的会话上下文或历史记录——你要精确构造它们所需的一切。这样也能为你自己保留用于协调工作的上下文。

**核心原则：** 每个任务一个全新子智能体 + 按流程图审查 = 高质量、快速迭代

## 流程

**本批要执行的 per-task 流程与示例工作流由 `codespec apply-subagent flow` 命令按测试模式动态返回，在开始执行任何任务之前第一步获取。**

在开始执行任何任务之前：

1. **确定测试模式并获取本批执行流程（关键，第一步）**：
   - 先读取 task.md 头部的 `测试策略` 标记（`tdd` / `test-after` / `no-test`）；未找到时默认 `tdd`。
   - 按该模式运行（缺省 flag 时命令默认按 `tdd` 返回）：
   ```bash
   codespec apply-subagent flow --tdd        # 或 --test-after / --no-test
   ```
   - 返回的 dot 流程图即本批实际要执行的 per-task 流程；返回的 example 即本批示例工作流（见下文「示例工作流」一节）。
   - 严格按返回图中的节点与边执行：只为图中出现的 agent 分派子智能体；不添加图中没有的审查步骤，也不跳过图中有的审查步骤。
2. 读取 spec.md, design.md 和 task.md，建立全局需求理解。
3. 提取所有任务的完整文本与上下文，创建 TodoWrite：**每个任务一个条目**（任务内的实现与图中该任务的各审查节点都是该条目的子步骤，**不要**为子步骤创建条目）。

  **TodoWrite 纪律（关键）：**
  - 在开始实现前，**必须**用 Todo 为所有未完成任务创建条目(**只跟踪任务，不要跟踪子步骤**)
  - 每完成一个任务后，**立即**将其标记为 completed
  - 不要批量标记——完成一个标记一个
  - TodoWrite 是 continuation enforcer 判断进度的基础，不遵守 = 系统误判

  **task.md 复选框同步（关键）：**
  - 每完成一个任务后，**同时**用 Edit 工具更新 `task.md` 文件中的任务复选框
  - 将对应任务的 `### [ ]` 改为 `### [x]`
  - task.md 路径：`codespec/changes/<change-name>/task.md`
  - 确保 task.md 中的复选框状态与 TodoWrite 完成进度保持一致

## 处理实现者状态

实现子智能体报告四种状态之一。根据每种状态进行相应处理：

**DONE：** 先执行「回归验证门禁」（运行受影响模块的既有测试 + 变更前后同命令基线对比）；门禁通过（无新增失败）后才进入流程图中的下一个审查节点。门禁未通过时**不得**进入下一个节点、**不得**标记任务 completed，必须按「失败处置闭环」把失败交回同一实现子智能体。

**DONE_WITH_CONCERNS：** 实现者完成了工作但标记了疑虑。在继续之前阅读这些疑虑。如果疑虑涉及正确性或范围，在审查前解决。如果只是观察性说明（如"这个文件越来越大了"），记录下来并继续审查。

**NEEDS_CONTEXT：** 实现者需要未提供的信息。提供缺失的上下文并重新分派。

**BLOCKED：** 实现者无法完成任务。评估阻塞原因：
1. 如果是上下文问题，提供更多上下文并用同一模型重新分派
2. 如果任务需要更强的推理能力，用更强的模型重新分派
3. 如果任务太大，拆分为更小的部分
4. 实施阶段为无人值守，只有在反复尝试仍无法通过时才暂停报告状态（最低优先级）

**绝不** 忽略上报或在不做任何更改的情况下让同一模型重试。如果实现者说卡住了，说明有什么东西需要改变。


## 回归验证门禁（所有测试模式都必须执行，含 no-test）

**为什么需要这道门禁：** `no-test` 限制的是"写测试"，不是"跑测试"。如果实现阶段从不运行受影响模块的既有测试，行为变化（错误的重构、路径被改短、公共接口语义变化）就不会产生任何可观测信号，控制者与审查者只能凭"看起来对"结案——这类信号缺失不会被任何后续审查节点补上。

**执行时机：** 每个任务的实现子智能体返回 DONE / DONE_WITH_CONCERNS 之后、进入该任务的下一个审查节点之前；以及全部任务完成、进入最终审查之前。**本门禁独立于 `codespec apply-subagent flow` 返回的流程图**：无论图中是否画出验证节点，本门禁都必须执行，不得因图中没有就省略。

**步骤（按顺序执行，不得合并或跳过）：**

1. **确定受影响模块与对应的既有测试**：按本任务「涉及文件」定位受影响的测试模块（如 `tests/<module>/test_<module>.py`）。测试命令从项目配置读取（`pyproject.toml` / `pytest.ini` / `tox.ini` / `Makefile` / `package.json` 等），**禁止猜测命令**。仓库中确实没有对应测试模块时，记录"该模块无既有测试"并结束本节点，继续流程。
2. **运行既有测试（变更后）**：用上述命令运行受影响模块的既有测试，完整记录命令、退出码、通过/失败数量与失败用例名集合 `F_after`。只运行与本次变更无关的测试不算通过本门禁。
3. **基线对比（变更前）**：用**同一条命令**、同一环境在**变更前**的代码状态下再跑一次（例如临时 stash 本次变更后运行，再恢复），记录失败用例名集合 `F_before`。禁止用"我记得之前是好的"代替这次运行。
4. **计算新增失败**：`F_new = F_after - F_before`，即"变更前通过、变更后失败"的用例。

**判定（阻塞式）：**

- `F_new` 为空 → 本节点通过，可进入下一个审查节点。
- `F_new` 非空 → **立即阻断**：不得标记任务 completed、不得进入下一个审查节点、不得进入下一个任务、不得输出"实现完成"。必须进入下面的「失败处置闭环」，直到 `F_new` 清空。
- 拿不到变更前基线（如工作区不可回退） → 按"变更后存在失败"处理，取最严格路径走完「失败处置闭环」。

### 失败处置闭环

1. **交回同一实现子智能体**：把 `F_new` 中的每个用例连同完整失败信息（命令、输出、断言差异）交给**同一个实现子智能体**修复，要求在**生产代码**中修复，而不是改测试。
2. **复跑**：实现者修复后，用**同一条命令**重跑受影响模块的既有测试，直到 `F_new` 清空。
3. **禁止的消解方式**：修改、删除、跳过既有测试的断言；给用例打跳过标记；把用例移出测试集合；削弱测试夹具；在生产代码里加特例分支绕过既有行为。
4. **唯一的"预期变化"通道**：只有当**官方/上游已发布的补丁、issue 或需求文档明确写明该行为变化**时，才可判为预期变化——此时必须在验证记录中给出**可核验出处**（链接、文件路径 + 行号，或提交号），并把该用例写入最终汇报交给用户。**"官方测试补丁会更新""这是设计意图""改动很小"都不是证据**，一律按回归处理并修复。
5. **修复后必须复审**：修复完成后重新走一遍流程图中该任务的审查节点（审查者复审），不得直接结案。

**记录要求（每个任务一份）：** 测试命令、退出码、`F_before`、`F_after`、`F_new`，以及每个新增失败的处理结论（修复内容 / 附可核验证据的预期变化）。**没有记录的验证 = 没有验证。**

## 示例工作流

本批的示例工作流不再硬编码于本技能，而是由 `codespec apply-subagent flow --<tdd|test-after|no-test>` 命令一并返回（JSON 的 `example` 字段，或文本输出的「示例工作流」一节）。其默认值为内置默认示例（以内置默认流程为例；自定义流程图同理，按返回的图执行），用户可在 `config.yaml` 的 `subagent-apply.<mode>.example` 中覆盖。

获取后，参照返回的示例理解控制者与子智能体之间的交互节奏（提问 → 实现 → 自审 → 按流程图审查 → 修复 → 重审 → 标记完成），并按本批实际返回的流程图执行。

> 注意：内置默认示例以 `tdd` / `test-after` 风格展示（含测试步骤）。当本批测试策略为 `no-test` 时，实现者不编写、不修改任何测试文件，示例中的"添加了测试 / N/N 通过"等**编写测试**环节应理解为编译检查与功能自审，而非单元测试；但**运行仓库既有测试做回归检测的环节不因此取消**——「回归验证门禁」要求的既有测试运行与变更前后基线对比，在任何测试模式下（含 `no-test`）都必须执行。

## 优势

**与手动执行相比：**
- 子智能体严格遵循 task.md 头部标记的测试策略（tdd / test-after / no-test）
- 每个任务全新上下文（不会混淆）
- 并行安全（子智能体不会互相干扰）
- 子智能体可以提问（工作前和工作中都可以）

**效率提升：**
- 无文件读取开销（控制者提供完整文本）
- 控制者精确策划所需上下文
- 子智能体预先获得完整信息
- 问题在工作开始前就被提出（而非工作结束后）

**质量关卡：**
- 自审在交接前发现问题
- 按流程图中的审查节点逐个审查
- 审查循环确保修复确实有效
- 任一审查者报告的每一项问题（关键/重要/次要）都必须完整交给实现子智能体处理，不得摘要、筛选、降级或只选择 bug/关键项
- 规格合规防止过度/不足构建
- 代码质量确保实现良好，验证编译通过
- 回归验证门禁：每个任务实现完成后运行受影响模块的既有测试，并做变更前后同命令基线对比；"变更前通过、变更后失败"的用例一律阻断结案，直到由同一实现者修复并复跑通过

**成本：**
- 更多子智能体调用（每个任务需要实现者 + 流程图中的审查者）
- 控制者需要更多准备工作（预先提取所有任务）
- 审查循环增加迭代次数
- 但能及早发现问题（比后期调试更省成本）

## 红线

**绝不：**
- 未经用户明确同意就在 main/master 分支上开始实现
- 跳过流程图中的审查节点
- 带着未修复的问题继续
- 只修“bug/关键”，跳过“重要/次要”
- 回传审查问题时自行摘要、筛选或只挑关键
- 并行分派多个实现子智能体（会冲突）
- 让子智能体读取计划文件（应提供完整文本）
- 跳过场景铺设上下文（子智能体需要理解任务在哪个环节）
- 忽视子智能体的问题（在让它们继续之前先回答）
- 在审查合规性上接受"差不多就行"（审查者发现问题 = 未完成）
- 跳过审查循环（审查者发现问题 = 实现者修复 = 再次审查）
- 让实现者的自审替代正式审查（两者都需要）
- **不按流程图顺序执行审查**（顺序由图中的边决定，顺序错误）
- 在任一审查有未解决问题时就进入下一个任务


**回归验证门禁（绝不违反）：**
- 以 `no-test` 为由跳过运行受影响模块的既有测试（`no-test` 禁止的是写/改测试文件，不是跑既有测试）
- 未做变更前后同命令基线对比，就宣称"既有测试无回归"或"测试通过"
- 把"变更前通过、变更后失败"的既有用例自行判定为"预期行为变化"并放行结案——"官方测试补丁会更新""这是设计意图"都不是证据，必须给出可核验出处（上游补丁/issue/需求文档的链接、文件路径 + 行号或提交号）
- 通过修改、删除、跳过既有测试，或给用例打跳过标记、在生产代码里加特例分支来消解回归失败
- 回归验证门禁未通过（存在新增失败且未闭环）时，标记任务 completed、进入下一个任务或输出"实现完成"

**审查取样范围（绝不违反）：**
- 把流程图中审查节点的取样范围缩到"本次改动的函数"，而不覆盖变更影响面（受影响模块的既有测试、相邻调用方、公共接口的其他调用者）
- 在分派审查者或实现者的 prompt 里预先写好"这是预期变化，不要当成缺陷"，却不给出可核验证据

**如果子智能体提问：**
- 清晰完整地回答
- 必要时提供额外上下文
- 不要催促它们进入实现阶段

**如果审查者发现问题：**
- 实现者（同一子智能体）修复
- 审查者再次审查
- 重复直到通过
- 不要跳过重新审查

**如果子智能体失败：**
- 分派修复子智能体并提供具体指令
- 不要尝试手动修复（上下文污染）

**子智能体步骤执行纪律：**
- **严格按步骤顺序** - 实现者子智能体必须严格按计划中的步骤顺序执行，不合并、不跳过、不重排
- **测试策略由计划驱动** - 计划 task.md 头部的 `测试策略` 标记（`tdd` / `test-after` / `no-test`）决定每个任务的步骤形态，必须严格遵循：
  - `tdd`：先写失败测试并确认失败，再写最小实现，再运行测试确认通过
  - `test-after`：先完成功能实现，再编写单元测试覆盖验收场景并运行通过
  - `no-test`：仅实现功能代码并编译检查，**禁止编写、修改或删除测试文件**（不新增、不改动、不动任何既有测试）；`no-test` **不禁止运行仓库中既有的测试**——运行既有测试属于回归检测，是「回归验证门禁」的必做项，不得以"不写测试"为由跳过

**Schema：** <schema-name>
**执行模式：** subagent
**进度：** 7/7 任务已完成 ✓


### 回归验证（受影响模块既有测试）
- 测试命令: `<命令>`
- 变更前失败数: <N> / 变更后失败数: <M>
- 新增失败（变更前通过、变更后失败）: <K>（必须为 0 才可结案）
